# VeldMap

Настольное приложение для работы со спутниковыми снимками: обход и поиск по
каталогу провайдера (Copernicus Data Space), скачивание продуктов в локальную
библиотеку и просмотр превью — в том числе снимков, которые не скачаны, прямо
из удалённого хранилища.

Построено как микроядро: нативный хост на Rust с рантаймом WebAssembly, а вся
прикладная логика — изолированные wasm-плагины, общающиеся через шину событий.

---

## Требования

| | |
|---|---|
| Rust | nightly (закреплён в `veldcore/rust-toolchain.toml`) |
| Цели сборки | `wasm32-wasip1` для модулей, `x86_64-unknown-linux-gnu` для хоста |
| Python | 3.10+ (кодогенерация и сборочные скрипты) |
| GPU | Vulkan |
| Линковка (Linux) | `clang` + `mold` |
| Кросс-сборка под Windows | `x86_64-w64-mingw32-gcc` |

Nightly нужен ровно ради одного: `-Zthreads=16` (параллельный фронтенд rustc)
в `veldcore/.cargo/config.toml`. Нестабильных возможностей языка в коде нет, и
на stable проект собирается — теряется только скорость компиляции.

Виртуальное окружение для кодогенерации (`buildgen/.venv`) создаётся
автоматически при первой сборке; его состав задан в
`buildgen/requirements.txt` и досогласуется сам, когда файл меняется.

Корень репозитория языконейтрален: проект мультиязычный, и `rust-toolchain.toml`
с `.cargo/config.toml` лежат внутри Rust-частей (`veldcore/`, `*/generated/`).
Cargo ищет их вверх от текущего каталога, поэтому сборочные скрипты всегда
зовут его из каталога соответствующего манифеста.

## Сборка и запуск

```bash
python3 buildgen/build.py          # релизная сборка: кодоген + все модули + хост
python3 buildgen/run-native.py     # запуск
```

Сборка проходит пять этапов: тесты buildgen, генерация
`generated/`-крейтов из схем, компиляция wasm-модулей в `build/plugins/`,
компиляция нативного хоста и юнит-тесты Rust (нативные, для чистой логики —
подробнее в [CLAUDE.md](CLAUDE.md#сборка-и-проверка)).

Кодогенерация переписывает файл, только если его содержимое изменилось: cargo
сверяет исходники по mtime, и перезапись тем же текстом заставляла бы
пересобирать все модули на каждой сборке.

Прочие команды:

```bash
python3 buildgen/build.py --debug                       # отладочная сборка
python3 buildgen/build.py --verbose                     # печатать запускаемые команды
python3 buildgen/build.py clean                         # удалить все артефакты
buildgen/.venv/bin/python -m pytest buildgen/tests      # только тесты buildgen
python3 buildgen/build.py --windows --dist-dir <путь>   # кросс-сборка + деплой
python3 buildgen/run-native.py --debug                  # запуск отладочной сборки
python3 buildgen/run-native.py --config <каталог>       # другой каталог конфигов
```

### Доступ к Copernicus

Каталог и скачивание требуют ключей S3 к Copernicus Data Space. Скопируйте
[`.env.example`](.env.example) в `.env` и впишите свои:

```
COPERNICUS_ACCESS_KEY=...
COPERNICUS_ACCESS_SECRET=...
```

Без них сборка и запуск проходят нормально, но `data-provider` не сможет ни
обойти каталог, ни подписать адрес. `.env` в `.gitignore`; как значения
попадают в конфиги — в разделе [Конфигурация](#конфигурация).

Логи и уровни логирования — в [CLAUDE.md](CLAUDE.md#диагностика).

## Архитектура

### Шина событий

Единственная форма общения между сервисами — публикация события,
fire-and-forget. Синхронных вызовов между модулями нет.

- Топик: `<сервис>/<топик>`, payload — protobuf-сообщение.
- Доставка по умолчанию — всем подписчикам топика. Топик, помеченный в схеме
  `targeted: true`, доставляется только одному адресату, названному по имени.
- Ответ на запрос — это ещё одно событие; отправитель сопоставляет его со своим
  запросом по корреляции. Она едет в конверте (`EventEnvelope.correlation_id`),
  а не полем доменного сообщения: топики-пары объявлены в схеме (`replies_to`),
  и стабы этих топиков принимают её отдельным аргументом — у остальных её негде
  указать. Модуль читает её через `veldsdk::correlation()`.
- Каждый подписчик — актор с собственной очередью: его обработчики выполняются
  последовательно, в порядке публикации.
- Хост подписывает каждое доставленное событие именем отправителя; модуль читает
  его через `veldsdk::event_publisher()`. Имена есть у всех сервисов: нативные
  модули публикуют под своими наравне с wasm (id 0 — только сам хост).

### ABI

Обращения в состояние хоста идут не через шину, а прямыми синхронными вызовами.

| Группа | Функции |
|---|---|
| Шина и логи | `veld_host_publish`, `veld_host_log` |
| Система | `veld_random_bytes` |
| Создание ресурсов | `veld_resource_alloc_cpu`, `veld_resource_alloc_buffer`, `veld_resource_alloc_texture`, `veld_resource_create` |
| Данные ресурсов | `veld_resource_read`, `veld_resource_write`, `veld_resource_upload_image`, `veld_resource_texture_size` |
| Владение | `veld_resource_transfer`, `veld_resource_grant_read`, `veld_resource_grant_write`, `veld_resource_free` |
| Графика | `veld_graphics_execute` |
| Задачи | `veld_task_kill` |
| Контекст вызова | `veld_input_len`, `veld_input_copy`, `veld_output_set` |

Создают ресурс четыре вызова, и все кладут запись в один реестр: `alloc_*`
берут скаляры (`size`, `w/h/format/usage`), `veld_resource_create` — вложенный
дескриптор (`graphics.ResourceRequest`: шейдер, пайплайн, сэмплер, view, bind
group и её layout). Граница между ними проходит по форме аргументов, а не по
виду ресурса; освобождает всех один `veld_resource_free`.

Запись в ресурс и заливка изображения — разные вызовы. У текстуры нет ни
смещения, ни частичного обновления, поэтому от `write(id, offset, data)` для
неё не остаётся ни одного осмысленного параметра.

Буфер глубины выделяется тем же `alloc_texture`, что и цветная текстура, —
форматом `TEX_DEPTH32_FLOAT`. Отличается он не только формулой пикселя: залить
в него нечего (пишет в него только растеризатор), цветным аттачментом он быть
не может, и `COPY_DST` ему не выдаётся. Все три правила выведены из одного
предиката (`format::is_depth`), чтобы им негде было разойтись. Пайплайн
объявляет работу с глубиной в `depth_stencil`, кадр прикладывает буфер в
`Submit.depth_texture_view_id`; без глубины оба поля пусты, и плоской отрисовке
этого достаточно — порядок там задаёт сама последовательность команд.

**Как сообщается об ошибке.** Способа два, и выбирает между ними один вопрос:
различает ли вызывающий причины отказа.

- Причин несколько — тегированный ответ: первый байт `0` (успех) или `1`
  (дальше текст причины). Так отвечают `read`, `write`, `upload_image`,
  `resource_create`, `graphics_execute`: у них отказ означает «нет прав»,
  «нет ресурса», «носитель только на чтение» или «не тот вид ресурса», и
  голым нулём это не разделить.
- Причина одна — число, `0` как «нет». Так отвечают `alloc_*` (не хватило
  ресурсов), `texture_size` (нет такого), `free`, `transfer`,
  `grant_*`, `task_kill` (не твоё либо нечего трогать). Текст здесь ничего не
  добавил бы, а тегированный ответ стоил бы аллокации на каждый вызов.

Каждый модуль экспортирует наружу: `init`, `handle_event`, `get_subscriptions`,
`get_service_name`, `veld_alloc`, `veld_free_wasm`. Имя сервиса на шине хост
берёт из `get_service_name` самого бинарника.

### Схема как источник истины

Топики объявляются только в `schema.yaml`. По ней кодогенератор
(`buildgen/generate.py`) собирает крейт `generated/`:

- диспетчер `handle_event`: топик → обработчик с типом payload из схемы;
- список подписок для `get_subscriptions`;
- типизированные стабы `crate::emit::*` для своих выходов и
  `crate::calls::<сервис>::*` для объявленных зависимостей;
- список промежуточных ответов среди подписок — по нему SDK ловит снятие
  запроса с учёта на прогрессе (см. [Фоновые задачи](#фоновые-задачи)).

Строковых топиков в коде модулей нет. Перед генерацией схема проверяется:
существование каждого типа, наличие топика у сервиса-производителя, наличие у
чужого топика payload-типа и его видимость потребителю (пакет чужого модуля
объявлен в `dependencies`), существование входа, названного в `replies_to`,
наличие ответа у входа с `cancellable: true`, однозначность терминального
ответа у запроса с несколькими ответами, совпадение `name:` схемы с именем
каталога, а также правила снимка (см. ниже). Тип топика объявляется ровно один
раз — у производителя; потребитель называет только имя, и выводится тип из
чужой схемы.

Структура схемы:

```yaml
name: пример
interface:
  inputs:                       # топики, которые принимает сервис
    on_do:
      type: module/DoRequest
      cancellable: true         # долгая работа: её позволено убить
  outputs:                      # топики, которые он публикует
    on_state:
      type: module/State
      snapshot: true            # состояние целиком: неизменившееся не уезжает
    on_do_progress:
      type: module/Progress
      replies_to: on_do         # ответ на свой же вход
    on_do_result:
      type: module/DoResult
      replies_to: on_do
      terminal: true            # конец операции (нужен, когда ответов больше одного)
dependencies:
  fs:
    subs: [on_read_result]      # чужие выходы, на которые подписываемся
    calls: [on_read]            # чужие входы, в которые публикуем
hooks: [hook_event]             # опциональные хуки жизненного цикла
```

`module/` в типе ссылается на `types.proto` самого модуля — и только так: своё
имя пакета, написанное развёрнуто, значит то же самое, но неотличимо на вид от
чужого, а чужое требует объявленной зависимости. Валидатор развёрнутое своё
отклоняет. Остальные префиксы — на пакеты из `veldcore/interface/` либо на пакет
модуля, объявленного в `dependencies`: чужой тип виден ровно тому, кто и так с
этим модулем говорит, и это валидатор проверяет тоже. Работает такое объявление только для самого сообщения
топика — вложенному полю нужен `import` в `.proto`, а его wrap-крейт не найдёт:
в путях поиска у него только свой каталог и `veldcore/interface/`.

Рукописная часть модуля — `src/module.rs`: он объявляет `Config`, `State`,
`hook_init` и свободные функции-обработчики, чьи имена совпадают с ключами
топиков в схеме. Хук `hook_event` вызывается после каждого обработанного
события.

**Снимок состояния — не команда, и схема их различает.** Топик, помеченный
`snapshot: true`, везёт состояние целиком: чего не прислали, того у подписчика
больше нет. Таких в проекте шесть — набор контуров и набор наложений у глобуса,
его же ход добычи тайлов, состояние библиотеки, состояние показа у канвы и
разметка у ui-service; прочие шестьдесят с лишним — команды и пары
«запрос-ответ». Рассылать снимок приходится на всякое изменение того, о чём он
рассказывает, а вызывающих у такой рассылки много, поэтому условие «а
изменилось ли» стои́т не у них, а в сгенерированном стабе: он помнит отпечаток
последнего отправленного тела и повтор не публикует (`veldsdk::snapshot`).
Забыть его негде, и двум его экземплярам негде разойтись. Спросить состояние
заново при этом можно — `crate::emit::resend::<топик>()` забывает отпечаток, и
ближайшая рассылка уходит непременно; так отвечает `data-library` на
`on_list`.

Помнит отправитель, и отсюда единственное правило: подписчик снимка не вправе
терять своё состояние. Убитый и поднятый заново потерял бы его молча, а
отправитель об этом не знает и повтора не сделает, — поэтому схема не сводит
`snapshot: true` с отменяемым потребителем. Не сводит она его и с `targeted`
(отпечаток один, а адресатов много) и с парой `replies_to` (ответ принадлежит
своему запросу и обязан уехать, совпади он хоть дословно).

### Ресурсы и права

Ресурс — это то, что живёт на стороне хоста и адресуется `ResourceHandle
{ id, size }`. Идентификатор, владение и освобождение у всех ресурсов общие,
а вот содержимое делится надвое — по тому, работает ли над ним чтение по
смещению.

**Байтовые** (`ResourcePayload::Data`) — `read(offset, size)` и `write` есть:

| Носитель | Что это |
|---|---|
| `Cpu` | обычная память хоста |
| `Range` | файл на диске или удалённый файл, читаемый HTTP Range-запросами |
| `Buffer` | буфер GPU |

**Непрозрачные** (`ResourcePayload::Gpu`) — байтового диапазона за ними нет:
текстура, view текстуры, сэмплер, шейдер, bind group и её layout, пайплайн.
Текстура здесь, а не среди байтовых, потому что прочитать её по смещению
нельзя — копия GPU→CPU остановила бы конвейер. Залить в неё изображение
целиком можно, но отдельным вызовом (`upload_image`), не записью со
смещением.

Чтение и запись идут по смещению и копируют только запрошенный диапазон в
память вызывающего. Для `Range`-ресурсов это означает, что гигабайтный файл
читается окнами и целиком в память не поднимается; `veldsdk::ResourceReader`
даёт поверх этого обычные `Read + Seek` окнами по 256 КБ, пригодные для любого
парсера.

У удалённого ресурса окно превращается в HTTP-запрос, и цена у него двойная:
около полусекунды на сам запрос и около секунды на мегабайт. Поэтому блок кэша
мелкий (512 КиБ — два окна читателя), а последовательный проход разгоняется сам:
промах, пришедшийся ровно туда, где кончился прошлый запрос, удваивает кусок до
восьми мегабайт, скачок в сторону сбрасывает разгон (`network/src/range.rs`).
Крупный блок на всех обошёлся бы дороже всего там, где чтений меньше всего: за
128 килобайтами головы и хвоста, которыми считается отпечаток источника, ехали
бы мегабайты — а это первое, что делает всякий показ.

Место под блоки одно на все открытые ресурсы, и вытесняется из него старейшее
в пуле, чей бы блок это ни был. Не по потолку на каждого: ресурсов открыто
столько, сколько попросил сценарий — у наложения это по растру на слой, включая
скрытые, — и потолок «на каждого» умножался бы на их число, оставаясь при этом
невидимым: блоки лежат в куче хоста. Общий потолок у пула один и назван числом —
`POOL_LIMIT`, 256 МиБ (`network/src/range.rs`). Вытеснять
своё тоже неверно — под давлением активный читатель выбрасывал бы то, что
сейчас же и перечитает, пока простаивающий сосед держит своё нетронутым.

Оборвавшееся чтение переспрашивается. Показ снимка живёт минутами и уходит в
сеть сотнями запросов, а соединение рвётся — оборванное тело ответа, сброс, 502
у шлюза; без повтора одна такая осечка стоит целого прохода производителя, а
сорвавшийся проход — ячеек, которых потребитель больше не просит. Повторяется
только то, что проходит само: на отказ по существу — 403 у истёкшей подписи,
404 у чужого адреса — ответ будет тот же самый, а пауза перед каждым блоком
растянула бы одно сообщение на минуты.

Гашение хоста такое чтение обязано спрашивать само. Оно живёт под синхронным
ABI памяти, а не под задачей, и отменить его снаружи нечем: на выходе оно
вполне может быть в полёте — рвущиеся соединения как раз и дают тот самый
обрыв. Уйти в сеть ещё раз ему нельзя, потому что таймеры рантайма разбирают
первыми и новый запрос паникует внутри реквеста; поэтому раннер поднимает флаг
раньше, чем роняет рантайм, а повтор смотрит на него перед самым выходом в сеть
(`veldmap_host_core::shutting_down`).

У каждого ресурса есть аренда: владелец, список читателей и список писателей.
Владелец может передать владение (`transfer`), выдать право чтения или записи
(`grant_read`, `grant_write`) и освободить ресурс (`free`). Проверки выполняет
хост на каждом обращении. Отзыва выданного права нет: гранты живут ровно
столько, сколько сам ресурс, а отобрать их у читателей — то же самое, что
освободить его. Единственное, что снимает их разом, — `transfer`: у ресурса
новый владелец, и списки читателей и писателей прежнего к нему не относятся,
поэтому раздавать права заново обязан он (так и устроен обряд делегирования
поверхности — сперва владение, потом гранты).

Право записи включает и освобождение — `free` пускает по нему же. Развести их
нечем: любое условие, временно закрывающее запись, закрыло бы владельцу и
освобождение собственного ресурса.

Ответ на «открой мне это» у всех одинаковый — `core.ResourceOpened`; его
публикуют `fs`, `network`, `data-provider` и `data-library`. Владение открытым
ресурсом переходит к заказчику. Общая часть этого обмена — в
`veldsdk::resource`: `requester`, `accept`, `hand_off`, `opened`, `discard`,
`release`; там же вся дисциплина владения — RAII-обёртка `OwnedResource` и
обряды `grant_read_or_free`/`grant_write_or_free` (при отказе делегирования
ресурс освобождается хелпером).

Последние два в списке — не синонимы, а противоположности, и путать их дорого.
`discard` отвечает на **чужой** ответ и ресурса не трогает: рассылка шины
доходит до всех подписчиков, и незнакомая корреляция — норма, а ресурс в таком
ответе к этому мигу вполне может быть уже нашим. `release` освобождает **свой**,
которому не нашлось дела: вкладку закрыли, запрос вытеснили.

### Фоновые задачи

Отдельной сущности «задача» в платформе нет: **задача — это событие в
полёте**. Заводить и закрывать её нечем и незачем — оба факта уже есть в
проходящем событии, и учёт по ним ведёт сам диспетчер.

Открывается учёт, когда публикуется **всякий** запрос с объявленным ответом;
закрывается, когда проходит его `terminal:`-ответ. Идентификатор операции —
`correlation_id` запроса, её владелец — паблишер, которого штампует хост. Ни то,
ни другое модуль не сообщает, а значит и разойтись с действительностью нечему.

Учёт заводится не ради одной отмены, и `cancellable: true` — свойство записи, а
не повод её завести. Держится на нём обещание, без которого шина была бы
ненадёжной: **терминальный ответ приходит всегда**. Упади исполнитель посреди
работы — конец операции договорит хост, тем самым топиком из той же строки
таблицы. Без учёта договаривать было бы не по чему, и заказчик ждал бы ответа до
конца процесса — молча.

Тем же ходом закрывается и публикация в топик, на который никто не подписан:
исполнителя нет, ответа не будет, и конец публикует хост.

```yaml
inputs:
  on_load:
    type: module/LoadImageRequest
    cancellable: true      # долгая работа — её позволено убить
outputs:
  on_load_result:
    type: module/LoadImageResult
    replies_to: on_load    # единственный ответ терминален по умолчанию
```

`terminal: true` пишут только там, где ответов у запроса несколько и выбор
действительно есть: у `network/on_fs_download` их два, и концом работы
является `on_fs_download_result`, а не прогресс. Забыть нельзя — схема с
неоднозначным концом не собирается.

Обратная сторона того же факта уезжает заказчику: кодогенератор отдаёт модулю
список ответов, которыми обмен **не** кончается, и `Correlator::take` с
`Latest::settle` пишут предупреждение, если их позвали на таком. Снять запрос
с учёта на прогрессе — значит не опознать следующий ответ и потерять
приехавший в нём ресурс, причём молча.

Знание одностороннее, и полагаться на него можно только в одну сторону.
«Промежуточный» — надёжный запрет: исполнитель пришлёт ещё. «Терминальный»
разрешением снять с учёта не является: ту же корреляцию заказчик вправе
продолжить следующим обменом к другому сервису — так делает `data-library`,
ведя закачку через `on_signed` в `network/on_fs_download` одним id. Где
кончается цепочка, знает только он.

Отсюда же и устройство учёта: под одним `correlation_id` обменов бывает
несколько. Сквозной запрос спрашивает следующий сервис тем же id, которым
ответит своему заказчику (`data-provider/on_open` → `network/on_open`), и пока
идёт внутренний, внешний тоже жив. Различает их терминальный топик — он у
каждого обмена свой, — и по нему же обмен закрывается: ответ внутреннего не
снимает с учёта внешний. Отдельной таблицы «а этот топик терминальный?» поэтому
нет вовсе: закрыть пытается всякая публикация, и не-терминальная просто ни с чем
не совпадает.

Что обещание покрывает и чего не покрывает, стоит сказать прямо. Хост отвечает
за **исполнителя, которого не стало**: упавший или снятый инстанс уносит
состояние целиком, и все обмены, которые он вёл, договариваются его концами —
не только тот, на котором упали. Асинхронный модуль иначе остался бы должен:
запрос он принимает в одном обработчике, а отвечает в другом, по чужому ответу,
и на том, втором, обмена в конверте уже нет.

Не покрыто два случая, и оба лежат выше платформы. Первый: модуль жив, но не
отвечает — потерял корреляцию, ушёл ранним `return`, ждёт ответа, который не
придёт. Учёт тут ни при чём: исполнитель на месте, и решить за него, что он
уже не ответит, платформе нечем. Второй: нативный сервис хоста падает с
`panic = "abort"`, то есть уносит процесс целиком, — ждать после такого некому
(в отладочной сборке паника уносит только задачу, но проверяется правками
релизная).

И одна оговорка про содержимое. Синтезированный ответ пуст, а пустое сообщение
proto3 — это все поля по умолчанию, то есть у многих ответов «всё хорошо, и
ничего нет». Отличается это от настоящего ответа только тем, что настоящего не
было; принимающему стоит помнить, что пустой терминальный ответ означает «конца
не дождались», а не «получилось».

Убивает операцию её владелец — сгенерированным стабом
`crate::cancel::<сервис>::<топик>(&correlation_id)`. Стаб есть ровно у тех
вызовов, чей топик объявлен `cancellable: true`: убить то, что отменяемым не
объявлено, — ошибка компиляции, а не молчаливый отказ в рантайме. Учтено при
этом и неотменяемое, но реестр про него знает, что убивать его нельзя, — так
что запрет держится не одним лишь отсутствием стаба. Это
ABI-вызов, а не событие: убийство меняет состояние хоста, как `veld_resource_free`,
и отвечает сразу. Отдельного сервиса `tasks` в платформе поэтому нет.

Убийство без церемоний. Нативного исполнителя снимает `abort` его фьючерса;
wasm-исполнителя — трап по эпохальному прерыванию, посреди любой строки, после
чего его Store отравлен и инстанс поднимается заново, теряя всё своё состояние.
Ничего не доделывается и не разматывается: это моделирует отключение
электричества.

Инстанс при этом уносится целиком, и это дёшево ровно потому, что события
доставляются ему строго последовательно (`Dispatcher::spawn_actor`): в полёте
у него ровно одно событие — то самое, которое и убивают, соседней работы
внутри нет. Заново собирается инстанс, а не бинарник — `Module` скомпилирован
один раз и переиспользуется, так что цена это новый Store и `init` (порядка
единиц миллисекунд, лог «поднят заново за»). Теряется при этом `State` инстанса —
отсюда и правило, кто вправе объявлять себя отменяемым (см. ниже).

Тем же способом кончается и разросшийся модуль: линейная память инстанса
ограничена гигабайтом (`INSTANCE_MEMORY_LIMIT`), сверх него `memory.grow`
отказывает, аллокатор внутри модуля обрывается трапом, и уносит он только
себя, а не хост. Это предел, а не рабочий режим: декодеры `image-tiler`
считают свою цену заранее и отказывают строкой задолго до него. Тем же
числом ограничен и байтовый ресурс, который модуль просит завести за себя
(`alloc_cpu`): поручить хосту больше, чем позволено держать самому, он
не вправе.

Отсюда два следствия, за которые отвечает платформа, а не прикладной код:

- **Деструкторы исполняет хост.** У убитого их не было, поэтому всё, чем он
  владел, возвращает реестр по lease (`free_owned_by`) — как система забирает
  дескрипторы у процесса, которому выключили питание.
- **Терминальный ответ приходит всегда.** Убитый его не пришлёт — его уже нет,
  — поэтому за него отвечает хост: публикует тот самый `terminal:`-топик с
  пустым payload, который декодируется в значения по умолчанию. У заказчика
  инвариант не меняется: ровно один конец операции, одним и тем же топиком,
  как бы она ни кончилась. Второго канала «задачу отменили» поэтому не
  существует, и отличить синтезированный ответ от настоящего заказчик не
  может — обрабатывать их по-разному ему всё равно нечем.

Корректность после убийства — свойство устройства участников, а не аккуратности
завершения. Отменяемым объявляет себя тот, кому нечего терять: `image-tiler`
не хранит состояния между вызовами вовсе, а его durable-состоянием — тайловым
кэшем — владеет неубиваемый `tile-cache`. Всё, что должно пережить обрыв, к
этому моменту уже на диске — `.part` остаётся точкой возобновления, сидкары и
тайлы пишутся атомарно (временный файл + rename), поэтому обрыв посреди записи
не оставляет полуфайла.

### Окно и графика

Окно объявляет модуль-владелец — ключом `window` в своём конфиге. Дальше:

1. Раннер публикует `app/on_window_resized` владельцу.
2. Владелец выделяет текстуру нужного размера, отдаёт её рендереру и аттачит
   текстуру хосту через `app/on_set_surface`.
3. Модули записывают render-команды через графический ABI; кадровый цикл
   раннера выполняет их в текстуры-цели и блитит поверхность окна в свопчейн.
   Всё, на что ссылается записанный кадр, разрешается и закрепляется в момент
   submit (см. `GraphicsDevice::execute`): модуль живёт своим актором и вправе
   освободить текстуру следующим же сообщением — раньше, чем цикл доберётся до
   очереди, — а кадр, собранный до освобождения, обязан дорисоваться тем, из
   чего был собран. Ошибка ссылки поэтому приходит ответом на submit — туда,
   где ошиблись, — а не предупреждением кадрового цикла спустя произвольное
   число сообщений.
4. Ввод и кадровые тики раннер публикует в `app/on_ui_event`.
5. Прогон по сценарию спрашивает, где на экране названный элемент
   (`app/on_locate_widget`), и рисующий отвечает местом
   (`app/on_widget_located`). Спрашивает раннер, потому что раскладку считает
   не он: сценарий называет элемент так же, как его называет разметка, а
   перевести это имя в прямоугольник может только тот, кто разметку разложил.
   Номер вопроса едет полем сообщения, а не корреляцией конверта: платформенная
   пара «запрос-ответ» сводит ответ со входом того же сервиса, а здесь вопрос —
   выход `app`, ответ — его же вход, и такой формы схема не выражает.

**Темп задаёт экран.** Кадровый цикл ждёт вертикальной синхронизации, и из его
витков растут кадровые тики модулей — то есть ограничитель у всего приложения
один. Это не про экономию: тик — обычное событие шины, очередь подписчика не
ограничена (см. `Subscriber` в dispatcher.rs), и модуль, которому кадр обходится
дороже витка цикла, отстаёт безвозвратно. Очередь растёт, а с ней и задержка
между нажатием и увиденным; сам модуль при этом выглядит здоровым — он
обрабатывает все события, просто всё более старые. Считает кадры один
ui-service и только за автором разметки — за тем, кто прислал ему `on_set_view`
(trace.log, `perf`): счётчик меряет по собственным часам, и его «частота»
расходится с оконной ровно тогда, когда тот перестал успевать. У `image-view`,
получающего кадровый тик, но разметки не шлющего, своего счётчика нет; его
отставание видно только по задержке между жестом и кадром. У `globe` счётчик
свой и про другое: он меряет не кадры, а чего стоит пересчёт желаемого — обход
сетки ячеек, которым выбирают уровень и набор видимых тайлов, — и отчитывается
по концу всплеска, а не по часам (см. `perf.rs`).

**Делегирование места под рендер** — обряд общий, и сообщение у него одно на
всех: `core.SurfaceDelegated`. Им владелец окна отдаёт поверхность окна
ui-service, и им же автор разметки отдаёт трёхмерному виду место под него
(`Viewport`). Выделение, раздачу прав и освобождение прежней текстуры держит
`veldsdk::surface::delegate`: пишет в неё названный рендерер, читают названные
показывающие, а владеет ею тот, кто её выделил, — `Delegated` владеющий, и
закрытая вкладка освобождает своё место, ничего для этого не делая.

У обряда есть и конец — `veldsdk::surface::revoke`, то же сообщение с пустой
поверхностью. Одного освобождения текстуры мало: view, сделанный по ней
рендерером, держит её живой в обход реестра, и рисовать в место, которого
больше никто не видит, тот будет до конца процесса.

Формат текстуры едет в том же сообщении, а не приходит рендереру откуда-то
ещё: формат — свойство именно этой текстуры, и второй его источник разошёлся бы
с ней ровно тогда, когда мест под рендер стало больше одного. Инъекции ключей
в init-конфиг у платформы поэтому нет вовсе.

`ui-service` — отдельный wasm-модуль: принимает разметку (`on_set_view`),
раскладывает её через iced, шейпит текст через cosmic-text в глифовый атлас,
собирает вершины и отправляет их графическим ABI в делегированную ему текстуру.
События виджетов возвращаются владельцу разметки адресным `on_ui_event`.

Цвета разметка называет в sRGB — так же, как их называют в макете и в CSS; в
линейное пространство их переводит рендерер. Поверхность окна sRGB-формата, и
записанное в неё GPU кодирует сам, поэтому отдать ему sRGB-число как есть
значит закодировать его дважды (см. `Vertex::color` в `ui-service/renderer.rs`).

### Разметка: что делать с нехваткой места

Раскладка выводится из содержимого, поэтому виджет, которому не хватило места,
не обрезается сам — он меняет форму и утаскивает за собой соседей. Правила ниже
не про красоту, а про то, чтобы одна длинная строка не разложила окно.

- **Что делать при нехватке ширины, текст объявляет сам.** Умолчание —
  перенос по словам (`WRAP_WORD`), а в имени файла, пути или ключе пробелов
  нет: такой текст в отведённую ширину не переносится, а выходит за неё и
  рисуется поверх соседа. Удержать его в рамке может только
  `wrapping(WRAP_WORD_OR_GLYPH)` — он рвёт неделимое слово по буквам, и высота
  подписи тогда растёт вниз, утаскивая соседей. Поэтому подписи в колонках
  фиксированной ширины, на кнопках и на вкладках объявляют `single_line()`
  (он же `NO_WRAP`): одна строка, а лишнее срезает коробка вокруг.
- **Хром постоянного размера фиксирует свою высоту.** Полоса вкладок,
  тулбар, статус — `Length::Fixed`: тогда ни один ребёнок не вправе растянуть
  их собой, что бы в него ни попало.
- **Содержимое шире места уезжает в прокрутку, а не сжимается.**
  `scrollable().direction(SCROLL_HORIZONTAL)`; без неё flex доводит детей до
  нулевой ширины, а текст нулевой ширины занимает высоту.
- **Навести прокрутку можно, удержать — нет.** `Scrollable.scroll_to` ставит её
  на названное место один раз на просьбу. Разметка пересобирается на каждое
  событие, и наводка, применяемая каждый кадр, держала бы список намертво:
  колесо крутилось бы, а он стоял. Просьба поэтому пронумерована, а не выражена
  одним смещением: к одной и той же строке приводят дважды подряд, и по
  смещению вторую просьбу от первой не отличить. Сколько это в строках, считает
  клиент — высота строки его, а не рендерера.
- **Настоящий перенос требует `Length::Fill` на обоих уровнях** — и на самом
  тексте, и на строке вокруг: `Fill`-текст внутри `Shrink`-строки реальной
  ширины от родителя не получает и схлопывается в минимальную.
- **Имя ребёнка (`Widget.key`) — не про подмену содержимого.** Оно говорит,
  где в списке произошли вставка или удаление; список той же длины
  сопоставляется позиционно, а разнородных детей именовать нельзя вовсе
  (см. комментарий у `Widget.key` в `veldmodules/ui-service/types.proto`).
- **Коробка обрезает содержимое по себе — всегда.** Рычага «не обрезать» у
  `Container` нет: коробка это граница показа, а не только место в раскладке.
  Иначе тесное окно рисует подпись поверх соседа и за краем панели — ужимает
  родитель коробку, а содержимое своей ширины не теряет. Рисовать поверх
  соседей умеет `Popover`, тем и отличается. Обрезка при этом не многоточие:
  срез приходится на середину знака, и осмысленный хвост ставит сам клиент —
  ширина знака у моноширинного шрифта одна, и по ней считается, сколько их
  влезет (`components::format` в `data-browser`).
- **Обрезка живёт в рендерере, а не в раскладке.** Ни `Container`, ни строка
  слоя не заводят: iced сужает детям границы и передаёт их отдельным доводом
  тому, кто рисует текст (`clip_bounds`). Значит, и применить их может только
  ui-service — он и ставит ножницы кадра тому тексту, который в границы не
  влез (`renderer::clipped`). Ножницы считаются в пикселях кадра: слой,
  открытый внутри переноса, сдвигается вместе с ним, иначе прокрученный
  список обрежется по месту, где содержимое стояло до прокрутки.
- **Отступ от краёв назначает кто-то один.** Поставленный и родителем, и
  ребёнком, он сужает колонки вдвое против расчётного — а тот, кто считал
  обрезку по своей ширине, об этом не знает и рисует поверх соседа. В таблице
  `data-browser` отступ ставит кнопка строки (она обязана быть нажимаемой и на
  полях), а шапке и заголовку группы его добавляет обёртка.
- **Всплывающее — это `Popover`, а не сосед в разметке.** Панель, положенная
  рядом с кнопкой, занимает место у соседей и режется ближайшей прокруткой;
  `Popover` рисует её оверлеем — поверх всего и без места в раскладке.
  Открыта она или нет, решает клиент: состояние меню принадлежит экрану.
- **Место под чужой рендер — это `Viewport`, а не картинка.** `WgpuImage`
  показывает готовое: вписывает текстуру в отведённое место по её собственным
  пропорциям и на указатель не отзывается. `Viewport` — место, которое владелец
  разметки рисует сам: у его текстуры собственного размера нет, размер ей
  назначает раскладка. Отсюда три отличия, и все три следуют из этого одного:
  область заполняет отведённое место целиком, перерисовывается каждый кадр
  (содержимое меняется без участия разметки, и по разметке об этом не узнать) и
  возвращает владельцу свой размер в пикселях и указатель в тех же пикселях.
  Обратной связи «размер текстуры → раскладка» при этом нет: место выведено из
  разметки, поэтому ответ владельца её не двигает, и цикл сходится за шаг.
- **Жест принадлежит разметке, а смысл жеста — тому, кто рисует.** Область
  отдаёт наружу указатель (`PointerEvent`), а не команды: какой кнопкой вращают
  и что делает колесо — решение об интерфейсе, и принять его можно только там,
  где виден весь экран. Во что превращается поворот, знает только рисующий.
  Поэтому `data-browser` переводит протаскивание в `globe/on_camera`, а сам
  `globe` о кнопках мыши не знает вовсе. Единицы у указателя такие, что
  переводить их не приходится: координаты — в пикселях текстуры области,
  прокрутка — в щелчках колеса. Пиксель прокрутки означал бы ровно то, во что
  его переводит сглаживание ui-service, и всякий получатель хранил бы у себя
  копию этого числа.
- **Кнопка — это коробка, на которую можно нажать.** Отдельного виджета под
  неё нет: нажимаемость объявляется полем `Container.interaction`, и всё, что
  коробка умеет — отступ, размер, выравнивание содержимого, обрезка, фон,
  рамка, — работает у кнопки тем же способом. Отдельный носитель этих полей
  повторял бы коробку и расходился бы с ней: недостающее у него — выравнивание
  содержимого, обрезку, фон — каждый call-сайт обходил бы лишней обёрткой.
  Состояния коробки называются по одному
  (`hovered`/`pressed`/`disabled`), и незваное вырождается к покою — почти
  всякой роли хватает двух лиц.
- **Переносимость — тоже свойство коробки.** Что берут мышью и куда это можно
  положить, объявляется полями `Container.drag` и `Container.drop` — по той же
  причине, что и нажимаемость: переносят обычно то, что уже нарисовано
  коробкой. Сам перенос ведёт ui-service, а владельцу разметки уезжает одно
  событие — то, чем перенос кончился (`DropEvent`: что принесли и в какой край
  зоны попали). Иначе и не выходит: пока вкладку несут, всё происходящее — это
  «курсор над той зоной, а теперь над этой», а где какая зона, знает только
  тот, кто раскладывал.
- **Граница между панелями — виджет, а не линия.** `Divider` отдаёт сдвиг
  курсора в точках, пока его тянут, и одно событие, когда отпустили. Сдвиг, а
  не новый размер соседей: размеры задал владелец разметки, и перевести точки
  в них может только он — виджет своих соседей не меряет и даже не знает, кто
  они.

### Панели экрана

Экран — дерево панелей: лист с вкладками либо деление надвое, у которого есть
ось и доля (`state::layout`). Панель — место, в котором лежат вкладки: у каждой
своя полоса, своя активная вкладка и свой «плюс». Дерево, а не пара половин,
потому что «поделить надвое» — не единственный способ сложить работу: список
слева, шар справа сверху и снимок под ним — это два деления, вложенных одно в
другое, и парой половин они не выражаются.

Складывают его переносом вкладки, а не отдельным «создать панель»: пунктом её
меню («перенести вправо»), броском в край чужой панели или в её полосу вкладок.
Отсюда следствие: пустых панелей не бывает — панель заводит вкладка, которая в
неё переезжает, а опустевшая уходит из дерева сама. Место, где ещё не решили,
что смотреть, — это вкладка (`ViewKind::Empty`), а не панель: у неё есть своё
место в полосе и свой крестик, как у всего остального.

Границы панелей тянут мышью. Разметка отдаёт сдвиг курсора в точках, а во что
он превращается в долях, считает тот, кто доли и задавал (`State::divide`):
деления бывают вложенными, и доля вложенного меряется не окном. Ни одна панель
не сходится в ноль — `MIN_PANE` держит предел, за которым в ней не видно ни
вкладок, ни того, что в них, а вернуть ей место было бы уже нечем.

Как экран сложили, таким он и откроется: раскладка пишется в
`runtime/state/data-browser.json` по каждому действию с вкладками и читается на
старте (`handlers::persist`). Сохраняется то, что определяет, **что показано**:
форма дерева, доли, род каждой вкладки и то немногое, из чего её содержимое
спрашивается заново, — папка каталога, условия поиска, снимок просмотра. Само
содержимое приходит ответом, и в файле ему делать нечего: список папки за
неделю станет другим, а показанный из файла был бы вчерашней правдой. Файл —
кэш, а не документ: не разобрался или пропал — окно открывается вкладкой из
конфига (`initial_view`), и спрашивается он только тогда.

Отсюда следует единственное правило проводки: **сообщение из тела вкладки
называет свою вкладку**. Панелей на экране сколько угодно, поэтому «активный
вид» на вопрос «чей это щелчок» не отвечает — щёлкнуть могли в той панели, что
не под рукой, — и всё, что рождается внутри вкладки, едет обёрнутым в
`Msg::In(ViewId, ViewMsg)`, а вкладка называет себя полем `Handler.key`. Именно
им, а не нагрузкой: у поля ввода, области и ползунка нагрузку изготавливает
рендерер, и адресату там места не осталось бы (см. `Handler` в
`ui-service/types.proto`).

Что делится, а что нет, выведено из того, чьё это свойство. Наложения на шаре,
контуры и каталог скачанного — свойства приложения, и панель их не делит:
«На просмотре» в любой из них показывает один и тот же набор слоёв, а
сообщение, действующее на них, вкладки-источника не несёт вовсе — адресовать
его некуда, оно одно на окно.

По той же причине вкладка, чьё содержимое принадлежит приложению, а не
панели, — синглтон: уже открытая показывается вместо второй такой же. Поиск и
скачанное — потому что их содержимое от вкладки не зависит; «На просмотре» —
потому что слои лежат в состоянии модуля; глобус — потому что рисующий модуль
один и место под рендер он принимает одно (`on_set_surface` имени вида не
несёт, в отличие от `Canvas` у `image-view`). Дублируются две — каталога и пустая:
две папки рядом обычное дело, ровно для этого вкладки и есть, а пустая тем
более, это место, а не вид.

Позванный из меню «плюса» синглтон переезжает в ту панель, откуда его
позвали: просили показать его здесь, а не отправить взгляд туда. Показ снимка
на шаре — не зов: открытую вкладку глобуса он не двигает, а лишь переводит на
неё взгляд (`nav::on_new_globe`). Снимок кладут, глядя на шар, и утащить его к
списку значило бы убрать с экрана то, ради чего всё и затевалось.

**Переход — не зов, а показ.** «Показать в каталоге» из строки, из полосы под
шаром и из «На просмотре» ведут в уже открытый каталог, а новую вкладку заводят
только если каталога нет вовсе (`nav::catalog`). Ищется он от ближнего к
дальнему — показанный в этой панели, любой в ней, любой в остальных, — и
найденный в чужой панели остаётся на месте, как остаётся глобус:
взгляд переводят к нему, а не тащат его к списку. Заводить вкладку под каждый
переход значило бы копить их, пока за ними не станет не видно работы; заводит
их по-прежнему меню «плюса», у которого об этом и просят.

Приведённая строка при этом называется трижды: каталог открывает её папку,
список встаёт на её страницу и подсвечивает её саму, а прокрутка наводится на
неё — `Scrollable.scroll_to` в разметке, один раз на смену значения. Иначе
строка, до которой довели, лежала бы ниже края экрана, и «привели» значило бы
«открыли ту же папку».

**Подсвечена одна строка на весь экран.** Подсвечивают её двое — переход к
строке и выбор контура щелчком по шару, — но отвечают они на один вопрос, «что
здесь главное сейчас», и двух ответов у него не бывает. Поэтому подсветка и
хранится одним полем на экран (`state::Highlight`): в нём ключ снимка, вкладка,
чей переход к нему привёл, и обведён ли он на шаре лентой. Каждый из двоих
пишет это поле целиком и тем самым гасит прежнюю подсветку; разложенная по
носителям, она держалась бы гашением из каждого обработчика, и подсвеченными
оставались бы обе строки — та, к которой привели полчаса назад, и та, которую
выбрали сейчас. Само по себе ни то, ни другое не выветривается: отметка
перехода живёт до ухода из папки, лента на шаре — до следующего щелчка. Тем же
правилом и по той же причине живёт раскрытое меню (`state::Open`): раскрытым
бывает только одно, и это свойство экрана, а не панели, вкладки или слоя.

**Имя в списке режется по тому, чем строки отличаются.** Обрезать середину —
правило по умолчанию, но у имён Copernicus совпадают как раз края: миссия с
типом продукта в начале, базовая линия обработки с расширением в конце.
Обрезанная посередине, страница каталога превращается в два десятка строк
«S3A_SL_2_A…R_003.SEN3», в которых не выбрать ни одной. Поэтому список считает
по показанной странице, что у имён совпало (`format::shared`), и срезает это
первым; освободившееся сверх различающегося возвращается началу имени — по нему
его и узнают (`format::distinct`). Правило отступает само: одно имя, имена,
совпавшие целиком, помещающиеся целиком, край короче двух знаков — режутся, как
прежде.

**Номеров в подвале столько, сколько влезает** (`controls::numbers`): окно
вокруг текущей страницы, края названы всегда, разрывы помечены многоточием. У
папки каталога страниц бывает под полсотни, в ряд они не помещаются, а коробка
режет по себе — и срезается при этом хвост ряда, то есть стрелка «дальше».
Список, у которого не видно ни одного способа уйти с первой страницы, выглядит
короче, чем он есть.

Таблица в панели не сжимается, а роняет колонки: панель у́же окна, а колонки от
этого не худеют, и тянущееся имя схлопнулось бы в ноль. Порядок,
в котором они уступают место, — от справочного к необходимому: загрузка, дата,
размер, состояние, формат и последним значок; имя и кнопки не уходят никогда
(`components::table::fit`).

`data-browser` собственных входов не имеет: он общается с остальными только как
потребитель и получает события своих виджетов адресным `ui-service/on_ui_event`.

У `globe` выходов два, и оба про то, чего по самой текстуре не видно.
`on_probed` отвечает, какое место на Земле пришлось под точку кадра;
`on_overlay_progress` — как идёт добыча тайлов у каждого наложения. Результат его работы —
та самая текстура, которую ему отдали, а вот перевести доли области обратно в
широту с долготой может только он: одна и та же точка кадра означает разные
места на разной высоте, и высота — у камеры.

**Координаты у глобуса настоящие.** Земля — эллипсоид WGS84, оси — ECEF
(EPSG:4978), широта — геодезическая; за переход к декартовым отвечает одна
функция (`globe/src/geodesy.rs`), и через неё ходит всё: поверхность, сетка,
камера, а дальше и контуры снимков. Через неё же ходят и потребители: файл
включён в wrap-крейт глобуса тем же приёмом, что `pyramid.rs` в wrap тайлера, и
`data-browser` считает «попал ли щелчок в снимок» ровно той арифметикой, которой
глобус этот снимок обвёл. Своя копия сошлась бы с ней на глаз и разошлась на
числах — а расхождение здесь означает снимок, очерченный в одном месте и
выбираемый в другом. Шар был бы не проще, а неверен: у него
нормаль выходит из центра, и та же самая широта означала бы точку на 21 км в
стороне — пятую часть плитки Sentinel-2. Разбиение поверхности идёт ровными
шагами по широте и долготе, поэтому растр в EPSG:4326 ложится на него линейно,
без пересчёта на пиксель и без искажения у полюсов.

**У Copernicus две службы, и провайдер ходит в обе.** Каталог (OData) отвечает
метаданными и ключей не спрашивает — читать его может кто угодно; хранилище (S3)
отдаёт файлы и требует подписи. Связывает их поле `S3Path` из ответа каталога:
это тот же путь, которым потом подписывают, открывают и качают. Держать их в
одном модуле стоит поэтому — найденное надо уметь тут же открыть, а раскладку
хранилища знает только он.

**Геометрия снимка пересекает две границы, и типов у неё два.** У провайдера
`Ring` — факт о продукте: где его сняли. У глобуса `Outline` — указание
рисовать. Свести их может только тот, у кого на экране и список, и шар, то есть
`data-browser`; глобус про поиск не знает и знать не должен, а зависимость от
провайдера дала бы ему знание об облачности и типах продуктов заодно. Цвета в
контракте нет по той же причине, по какой в `CameraCommand` нет кнопок мыши: как
выглядит контур, решает тот, кто рисует.

**Отсюда общее правило: между модулями, не знающими друг о друге, тип не
разделяется, а переводится на границе.** Переводит его тот, кто с обоими и
говорит. Так живут не только кольца: `GeoPoint` объявлен и у провайдера, и у
глобуса; `UtmFrame` — трижды, считая рамку MGRS внутри самого провайдера;
`ImageryRole` становится `OverlayRole` полем в поле. Выглядит это дублем, и
соблазн свести всё в общий пакет велик — но общий пакет и означал бы ту самую
дугу, которой здесь нет: глобус узнал бы, что провайдер существует. Четыре
строки, переписанные дважды, дешевле этого знания, и переписаны они не по
недосмотру.

Взять чужой тип схема при этом умеет: модуль, объявивший другого в
`dependencies`, вправе назвать его пакет прямо в `type`. Но одинаковая форма
ещё не значит одинакового утверждения, и `TileResult` тому пример. У тайлера
это «тайл готов», у кэша — «тайл нашёлся»; поля совпадают, а сказано разное, и
потребители обоих зовут их `ProducedTile` и `CachedTile` именно потому, что
путать их нельзя. Свести их в один тип значило бы вдобавок заставить всякого,
кто слушает тайлера, объявить у себя ещё и кэш — связь, которой у него нет.

Так что читать эти повторы надо не как дубль, а как границу — ту, где модули
друг о друге не знают. Там, где дуга есть, ничего не переводится: и глобус, и
канва берут `Described` и `TileResult` у тайлера как есть, через его
wrap-крейт, и разводят два одноимённых типа переименованием при импорте.

**Три состояния строки, и они независимы.** Коробочка — **выбор**: набор для
пакетных действий, удалить и скачать. Значок многоугольника — **контур**:
очерчен ли снимок на шаре. Значок шара — **показ**: лежит ли он там растром.
Сведи любые два в одно, и одно начнёт отвечать за другое — снятый контур уносил
бы набранное к удалению, а показ клал бы снимок в состав пакетного действия,
которого никто не просил. Активное горит зелёным, поэтому по строке видно, что
именно с этим снимком сейчас сделано.

Контур и показ — переключатели, и механика у них одна: нажали — снимок на шаре,
нажали ещё раз — снят. Двух правил здесь быть не может, потому что вопрос у них
один — лежит ли этот снимок на шаре, — и разница только в подробности, с какой
он там лежит. Камеру ни один из них не двигает: **наводка** — третье намерение
и третий значок (перекрестье). «Покажи здесь» и «отвези меня туда» сведённые в
одно нажатие отбирают друг у друга ответ — положить второй снимок рядом с
первым становится нельзя, не улетев к нему.

Контуры одни на приложение, а не на вкладку: шар один, а списков сколько
угодно, и «контуры этой вкладки» на вопрос «что на шаре» не отвечает. Живут они
в `State::outlines` — это просьба, а не нарисованное: геометрию знает каталог,
ход к нему сетевой, и между нажатием и контуром проходят секунды. Значок
поэтому зажигается сразу и объясняет разницу подсказкой: «спрашиваем каталог»,
«геометрии нет», «очерчен». Выбор, наоборот, свой у каждого списка — им и
действуют над списком. Выдача сама по себе шар не очерчивает: полсотни найденных
плиток — это сетка поверх Земли, за которой не видно ни одной.

Значков у строки снимка не больше трёх, и все три про шар. Всё остальное —
скачать, приостановить, открыть, посмотреть — стои́т пунктами меню: строка
узкая, панель делят пополам, и значок сверх этих отнимал бы место у имени. А эти
место оправдывают тем, чего пункт меню не умеет: каждый говорит о своём
состоянии цветом. Наводка при этом бывает выключенной — у снимка, которого на
шаре нет, наводить не на что, — и стои́т она тогда цветом линии, а не чернил:
пропасть ей нельзя, иначе соседние значки съезжали бы на её место при каждом
нажатии, а обещать нажатие она не вправе.

Пакетные действия стоят значками в заголовке списка и появляются только тогда,
когда им есть что сделать: выбрать можно и то, чего нет на диске, и то, что уже
скачано целиком, а видная кнопка, которой нечего сделать, обещает действие и не
совершает его. Отвечает на это тот же разбор, каким потом пойдёт и само
действие — второй ответ на вопрос «что будет сделано» разошёлся бы с первым.

Оба разворачивают снимок в файлы: библиотека ведёт учёт файлам и о снимках не
знает — удаление берёт его записи (`files_of`), закачка сперва спрашивает
провайдера, из чего снимок состоит. Пакетное «скачать» при этом не то же, что
пункт у строки: там это переключатель и второе нажатие ставит закачку на паузу.
Файл разбирается точно — доведённый и идущий пропускаются, оборванный
докачивается; снимок пропускается только доведённый целиком, потому что чего в
нём недостаёт, знает провайдер, а не мы.

Выбор снимается с того, что действительно ушло удалению, и только с файлов: в
«Скачанном» строки за удалённым файлом больше нет, и оставшийся выбор считался
бы в заголовке до конца сеанса. Снимок остаётся выбранным — удалены его файлы с
диска, а сам он живёт в каталоге. Ни «Снять с шара», ни удаление контура выбора
не трогают вовсе: коробочка про другое.

Выбранная строка не только носит галочку, но и залита — слабее подсвеченной:
подсвечено на экране одно, а выбрано бывает полсписка, и равная заливка стёрла
бы разницу между «это главное сейчас» и «этих я набрал». Заливок поэтому четыре, и
старшинство у них названо в самой роли (`theme::RowTint`): состояние коробки
рендерер выбирает целиком, а не подмешивает к покою, так что «отмечена и под
курсором» протоколом не выражается — свести их в один цвет обязан тот, кто цвет
и называет. Оттуда же правило «наведение никогда не светлее покоя»: общий ховер
светлее акцентной заливки, и подсвеченная строка под курсором теряла бы
подсветку.

Геометрия при этом под рукой не у всех: у найденного продукт с контуром уже
есть, а у строки каталога или файла на диске — один ключ, и продукт по нему
восстанавливает провайдер (`on_locate`). Ответы кэшируются: ключ строки не
меняется, а ход к каталогу сетевой. Щелчок по шару выбирает из очерченного
самый мелкий контур — одну съёмку каталог отдаёт несколькими продуктами, — и
выбранный называет полоса под шаром: оттуда его смотрят и оттуда же находят в
каталоге. На самом шаре он обведён не линией, а лентой: линия в пайплайне
всегда в пиксель шириной, и цвет от цвета на такой ширине глаз почти не
различает. Ширина ленты экранная — в мире она зависела бы от приближения: на
отлёте расплылась бы в пятно, вблизи истончилась бы в ту же линию. Разводит
вершины в стороны вершинный шейдер, которому размер кадра приезжает вместе с
камерой (`vs_ribbon` в globe.wgsl), а невыбранные контуры при этом рисуются
вполсилы — чтобы не спорить с лентой за взгляд.

**У снимка, который на шар только едет, заштрихована вся занятая им область.**
Обведён он при этом обычным контуром: сказать надо не «этот снимок особенный», а
«место занято» — где ляжет и сколько возьмёт. Нужно это затем, что между
нажатием значка и первой картинкой лежат десятки секунд — ход к каталогу,
открытие растров, описание растра по сети, — и всё это время на шаре не
появляется ровно ничего; нажавший не видит даже места, куда снимок ляжет.

Штрих кладётся косыми полосами по кадру, а не по миру: в мире шаг зависел бы от
приближения — на отлёте область слилась бы в сплошную заливку, вблизи штрих
разъехался бы на пол-экрана. А сама заливка — веер от середины кольца к его
краю: контуры съёмок выпуклые (четырёхугольник или полоса), и у выпуклого
кольца веер из середины и есть точное разбиение; разбор на уши стоил бы
вдесятеро дороже ради случая, которого у съёмок не бывает. По радиусу веер
разбит так же мелко, как уплотнено кольцо, и по той же причине: треугольник от
середины до края — это хорда, и уже на градусе дуги её середина уходит под
поверхность глубже, чем контур над ней поднят, где её съедает тест глубины.
Кольцу, разошедшемуся на пол-Земли, середины нет вовсе — так записан пояс
климатической сетки, от −180 до 180, — и заливки у него не будет; контур
останется, а он и есть главное.

**А боковых краёв у такого пояса нет вовсе.** Записан он прямоугольником, и
его левая и правая стороны отличаются долготой ровно на круг — то есть это
один и тот же меридиан, пройденный вверх и вниз. Нарисованный, он и выглядит
как лишняя дуга поперёк двух колец, от края пояса до края — у климатической
сетки от 70° южной широты до 70° северной; вершин на нём набирается больше
половины всего контура.

Поэтому контур обводится не одной ломаной, а петлями: рёбра, которые не ведут
кольцо, а только переходят с края на край, не рисуются. Узнать их по одному
нулевому размаху долгот нельзя — нулевое ребро бывает и настоящим краем, — и
спрашивают о пробегах между такими рёбрами: замкнулся ли пробег сам (шов
соединяет то, что и без него одно место) и обошёл ли он Землю. У пояса из
четырёх вершин пробеги дают полный круг; у сетки с прорезью в десять градусов
— нет, и её края остаются на месте; у кольца, спустившегося по широте, концы
не сходятся, и его край тоже цел.

От числа вершин признак не зависит, а вот от того, где они стоя́т, — зависит:
размах каждого ребра отсчитывается по ближней стороне, и сумма пробега
сохраняется, только пока ни одно ребро не длиннее полукруга. Пояс, записанный
четвертями, режется; он же, разбитый пополам, — уже нет, и рисуется как
прежде.

**Управление шаром меряется тем, что видно, а не высотой.** Протаскивание на всю
высоту области поворачивает Землю ровно на ту дугу, которая в этой области
умещается: на отлёте это полторы сотни градусов, у самой поверхности — тысячные
доли градуса. Поэтому земля идёт за курсором на любом приближении, а не улетает при
малейшем движении вблизи. Той же величиной задаётся и наводка: `Focus` называет
место и угловой радиус того, что должно поместиться в кадр, а во что это
превращается — дело камеры (`globe/src/camera.rs`). Обе величины — прямая и
обратная одна другой, и считает их одна функция.

**Приближаются к тому, на что смотрят.** Место под курсором остаётся под
курсором: колесо приезжает вместе с точкой кадра, которую надо удержать, и
камера доворачивается на разницу двух дуг — от подкамерной точки до
удерживаемого места с прежней высоты и с новой. Считается это в два хода, и
второй не лишний: дуга сферическая, а поворачивают ею геодезическую нормаль, да
и высота отмеряется по нормали, тогда как кадр смотрит в центр. Оба промаха
вместе уводили бы вид на пиксель за щелчок — и уводили бы всё сильнее, потому
что каждый следующий щелчок увеличивает уже уехавшее. Поэтому после поворота
место спрашивается ещё раз, уже точное, и рамка доворачивается на то, чем оно
разошлось с обещанным; остаётся от пикселя сотая доля. Тем же ходом снимается и
боковой снос у приближения в середину кадра, где удерживать, казалось бы,
нечего.

**Поправка эта раскладывается надвое, и это не тонкость.** Невязка бывает
вдоль радиуса кадра и поперёк него, а градус угла стои́т в этих двух
направлениях разной дуги: вдоль — того, насколько дуга обгоняет угол, поперёк —
тангенса дуги, делённого на угол, потому что доворот идёт вокруг оси, лежащей в
плоскости дуги, и место обходит её по кругу. У середины кадра оба сходятся, а
дальше от неё расходятся на четверть и больше; приложенное поперёк радиальное
оставляет до пикселя невязки там, где верное оставляет десятитысячные. Порознь
двух проходов хватает на всю полосу высот с запасом в сотню раз.

У самой кромки силуэта удержание слабеет — не ради арифметики, а потому, что
удерживать там нечего: поверхность уходит из-под луча, один пиксель кадра
накрывает километры, и дрогни курсор на пиксель — под ним оказалось бы другое
место. Без этого щелчок у самой кромки разворачивал бы шар на шестую часть
кадра, а пикселем дальше — уже ни на сколько, потому что там луч уходит мимо
Земли. Мерка «вскользь» — косинус угла, под которым луч встречает землю: во
сколько раз больше земли накрывает пиксель, чем накрыл бы в надире, — только
обратной величиной; вдвое — выбор, и выбран он по ширине полосы, на которой удержание слабеет: у
кромки косинус падает круто, и при большем пороге полоса сжимается до десятка
пикселей курсора, то есть кромка дёргает вид по-прежнему.

Хватка спрашивается с обеих высот сразу — нынешней и той, куда едут, — и
берётся меньшая: отдаляясь, камера уменьшает диск, и место, которое держалось,
оказывается за силуэтом. Пара эта симметрична, и в этом всё дело: у щелчка
назад те же две высоты, значит и хватка та же, значит он отменяет щелчок
вперёд — а спроси хватку по одной высоте, и не отменял бы.

Щелчок колеса у шара и у канвы просмотра один и тот же: колесо одно, и два
разных шага у него — это то, чего пользователю неоткуда узнать. Множится при
этом разное — у канвы масштаб, у шара высота, — и у поверхности это одно и то
же, а на отлёте шар растёт медленнее: угол, под которым он виден, высоте не
пропорционален. От умолчательных четырнадцати тысяч километров до пола выходит
сорок четыре щелчка.

**Камера — рамка, а не пара углов, и полюса у неё нет.** Хранятся два орта:
куда она смотрит и что на экране сверху; широта с долготой выводятся из первого,
когда о них спрашивают. Жест поэтому не приращение координат, а один поворот
вокруг оси, составленной из осей кадра, — отсюда три следствия. Дуга выходит ровно та, о которой
просили, на любой широте, и разгонять горизонтальный жест на 1/cos(широты)
не нужно вовсе. Полюс переезжается: камера идёт через макушку и выходит с той
стороны, а не упирается в предохранитель, не доходя до неё. И базис не
вырождается — «верх» кадра хранится, а не выводится каждый кадр из оси мира,
которая ровно над полюсом сходится с направлением взгляда.

Плата за это одна, и она честная: перевалив макушку, кадр оказывается севером
книзу — то же, что видно из окна самолёта. Доворачивать его жест не берётся, это
провернуло бы мир на пол-оборота на глазах; север возвращают тем же
протаскиванием обратно либо наводкой на любой снимок — `Focus` ставит север
кверху. Жест и точно обратный ему друг друга снимают — и косой тоже, потому что
поворот один: разбитый на рыскание и тангаж, он снимался бы обратным лишь в
пределе мелкого шага. А обвод курсора по кругу возвращает вид повёрнутым на
площадь обойдённого, и вот это уже свойство сферы, а не здешней арифметики:
никаким выбором оси его не снять.

**Наводка едет, а не прыгает.** `Focus` называет цель, а ведёт к ней кадровый
тик — за шесть десятых секунды, плавно трогаясь и плавно вставая. Скачок через
полшара не читается как перемещение: вид просто становится другим, и куда делся
прежний, приходится соображать. Ориентация при этом интерполируется
кватернионом — единственное место в проекте, где он заведён, и заведён ровно
потому, что здесь он сильнее рамки: вести пару ортов покомпонентно значит идти
по хорде и выправлять результат Грам–Шмидтом, то есть идти не тем путём и
притворяться, что тем. Высота ведётся долями, а не метрами, — приближение это
умножение, — а любой жест перелёт отменяет: тянуть камеру в две стороны разом
незачем.

### Снимок и его части

Каталог CDSE считает продуктами, а человек — снимками, и это не одно и то же.
Одну съёмку Sentinel-1 каталог держит пятью продуктами разом: сырьё приёмника
(`IW_RAW__0S`, 1,2 ГБ), снимок уровня 1 полосным TIFF (`IW_GRDH_1S`, 1,6 ГБ),
он же тайловым COG (`IW_GRDH_1S-COG`, 739 МБ), комплексный `IW_SLC__1S` (6,6 ГБ)
и производные величины `IW_OCN__2S` (69 МБ). Одну пятиминутную гранулу
Sentinel-5P — десятью газами над одной и той же полосой земли. Показать из них
можно один, скачать осмысленно — любой, а десяток одинаковых с виду строк на
одну съёмку — это список, в котором ничего не найти.

Поэтому наружу провайдер отдаёт **снимок**, а продукты каталога сводит в его
части (`scene.rs`, `DataProduct.parts`). Связывает их то, что сказал сам
каталог. Первым — **дататейк вместе с номером слайса**: дататейк это
непрерывный отрезок съёмки, режется он на слайсы, и номер слайса — единственное,
чем все пять продуктов Sentinel-1 выше названы одинаково. Секунда на его месте
не годится, и разница не тонкая: нарезка у сырья своя, начало его слайса
отстоит от обработанного на четыре секунды, у комплексного — на полторы, и
границу секунды они пересекают почти всегда. По секунде одна съёмка
показывалась бы тремя строками из пяти возможных.

Номер слайса каталог сообщает не всем частям — у `IW_OCN__2S` его нет вовсе, —
и такая часть прикладывается к тому слайсу, рядом с которым снята
(`scene::beside_a_slice`): десять секунд по обе стороны с запасом накрывают
своё и с запасом не дотягиваются до соседнего слайса, стоящего в двадцати пяти.

А сам дататейк каталог сообщает не всему архиву: до осени 2023 года его нет ни
у одного продукта Sentinel-1 — девять лет из двенадцати. В имени он при этом
стои́т всегда, шестнадцатеричным полем сразу за парой времён съёмки и номером
витка, и оттуда его и берут (`scene::datatake_in_name`). Ищется он от пары
времён, а не по счёту полей: у `WV_SLC__1SSV` тип занимает два поля с пустым
между ними, а у тайловой укладки в конце добавлен `_COG`.

Дальше — плитка сетки вместе с секундой (так лежит Sentinel-2), затем виток
вместе с прибором и секундой: так лежит Sentinel-5P (`orbitNumber=45811`,
`TROPOMI`). Прибор нужен затем, что на борту их бывает несколько: Sentinel-3
снимает двумя разом, и два его продукта одной секунды одного витка — два разных
снимка. Не связал каталог — снимок остаётся сам по себе; исключение одно и
узкое: имена, расходящиеся только хвостом укладки (`…_V3.0.1_cog` и
`…_V3.0.1_nc` у климатики), — это заведомо одна и та же величина в двух
форматах, и узнаётся такой хвост независимо от регистра и от того, стои́т ли он
перед расширением (`…_675b_COG.DIMA`).

**Показывается та часть, которую можно показать**, и порядок предпочтения
задан правилом, а не списком миссий (`scene::rank`): сырьё уровня 0 последним
всегда — изображения в нём нет вовсе, — перед ним продукт, у которого уровень не
объявлен вовсе (так лежат аннотации вроде `IW_ETA__AX`), дальше уровень по
возрастанию, тайловая укладка вперёд полосной (её читают окном, а полосной верхний уровень пирамиды
стоил бы чтения всего файла), при прочих равных меньшая. Отсюда и то, что
нажатие «на глобус» у сырого продукта кладёт на шар нормальный снимок: спросили
про съёмку, показывается съёмка. Продукт, восстановленный по ключу
(`on_locate` — строка сетевого каталога или загрузок), доспрашивает соседей
вторым ходом к каталогу — временем съёмки, потому что имена у частей расходятся
хвостом. Ширина окна идёт за правилом сведения: спросить у́же, чем сводишь, —
значит не увидеть в ответе того, кого собирался приложить. Там, где дататейка
нет, секунда съёмки стои́т внутри самого ключа, части начинаются в одно
мгновение, и хватает секунды по обе стороны. Там, где дататейк есть, части
нарезаны порознь и расходятся началом, а правило «по слайсу» времени не
ограничивает вовсе — своей границы у запроса нет, и берётся она у
`beside_a_slice`: те же десять секунд.

**А вот подменять спрошенное соседкой можно только дважды** (`scene::about`):
когда у спрошенного изображения нет вовсе (уровень 0) и когда рядом лежит **та
же величина** в тайловой укладке вместо полосной. Во всех прочих случаях
показывается то, о чём спросили: части одной съёмки бывают разными измеренными
величинами, и ответить на вопрос об угарном газе озоном — пусть даже озон вдвое
дешевле — значит соврать.

**Значок «на глобус» гаснет там, где показывать заведомо нечего, и говорит
почему** (`imagery::unviewable`, `DataProduct.unviewable`). Ответов честных
два: «нет» — сырьё уровня 0 и продукт-файл с нечитаемым расширением (архив
таблиц `.TGZ`); и «похоже, да» — всё остальное. Отказ едет причиной, а не
флагом: значок, пропавший без объяснения, оставляет смотрящего гадать, а
отказы эти разные, и различить их снаружи можно только словами. Место за
значком остаётся, причина живёт подсказкой — тем же способом, каким
объясняется наводка на снимок, которого на шаре нет. В тесной панели, где
значки уезжают в меню пунктами, выключенный не уезжает и объяснения не
доносит: пункт меню, который ничего не делает, не объясняет и себя. О папке без листинга сказать нечего, и предлагать
её честнее, чем отказывать: раскладок много, листинг стоит запроса, а не
найденный в ней растр объяснит `imagery::nothing_here`.

**Не снимок — то, у чего нет контура.** Вспомогательные данные (калибровочные
таблицы, эфемериды) каталог отдаёт продуктами наравне со съёмкой, и по свежести
её обгоняют: срок действия таблицы записан будущей датой, и в «самом свежем» они
занимали треть страницы. Очертить их на Земле нечем, показать нечем — в списке
снимков им не место. Правило механическое и одно на все миссии: вышел из
геометрии каталога контур — снимок, не вышел — вспомогательные данные. Именно
разобранный контур, а не присутствие поля в ответе: геометрия бывает и такой,
из которой колец не выходит, и снимок тогда оставался бы в списке, не
очерчиваясь ничем. Кольцом при этом становится и ломаная: у надирного прибора
снятое и есть линия, а не площадь, и `LineString` каталог отдаёт всей
альтиметрии.

**У запроса к каталогу всегда есть нижняя граница по времени.** Это не про
выдачу, а про скорость, и цена вопроса такая: без границы каталог сортирует весь
архив — пустой запрос отвечает за 21 секунду, запрос по области за минуту,
запрос по облачности не отвечает вовсе; с границей те же три занимают 3, 6 и
1,5 секунды. Не назвал границу заказчик — её ставит провайдер
(`catalogue::FRESH_DAYS`), и она не окончательна: кончились в окне продукты, а
страница снимков не набралась — тот же запрос уходит второй раз уже без неё, и
медленный ответ каталога тогда оплачен делом. Просит провайдер вчетверо больше
продуктов, чем нужно снимков (`OVERFETCH`): каталог считает продуктами, а
страницу мы набираем снимками. Поэтому «кончились» — это про продукты, а не про
снимки: полная страница продуктов при короткой странице снимков означает не
пустое окно, а сведение, и расширять его незачем.

### Поток просмотра

Снимок показывается тайлами пирамиды: уровень n — источник, ужатый в 2ⁿ раз,
вершина помещается в один тайл 512². Показ ведёт `image-view` (канва), байты
режет `image-tiler`, готовое лежит у `tile-cache`:

```
data-browser --on_open--------> data-library | data-provider  (открыть ресурс)
data-browser --on_show--------> image-view       (владение ресурсом — канве)
image-view   --on_describe----> image-tiler      (размеры, уровни, отпечаток)
image-view   --on_query-------> tile-cache       (тайлы с диска + промахи)
image-view   --on_produce-----> image-tiler      (произвести промахи; отменяемо)
image-tiler  --on_store-------> tile-cache       (всё произведённое, попутно)
image-view   --on_view_state--> data-browser     (масштаб, прогресс, ошибка)
```

**Потребителей у пирамиды двое, а механика одна.** Канва просмотра и наложения
на шаре ведут один и тот же танец — описать источник, выбрать уровень, спросить
у кэша недостающие ячейки, промахи отдать производителю, приехавшее сложить в
видеопамять и вытеснить оттуда давно не рисовавшееся, — и различаются ровно
одним: какие ячейки видно прямо сейчас. Поэтому вся эта механика живёт в одном
месте, у самой пирамиды (`veldmap_image_tiler_wrap::tiles`, тем же включением,
что и `pyramid`): хранилище тайлов с бюджетом, выбор уровня, учёт спрошенного и
учёт идущих проходов, годность описания источника и признак «работа идёт».
Каждый потребитель приносит туда только своё — уровень под экранный пиксель и
ответ на «что из этого уровня видно»: канва считает их камерой над картинкой,
глобус — привязкой и матрицей кадра. Сообщения кэшу и производителю при этом
шлёт он же: топики объявлены в его схеме, и публиковать за него wrap не вправе.
Своё у каждого и то, **как показать отказ**: у канвы для причины есть место на
экране, у наложения только лог — растров у него два, и отказавший один
оставляет слой жить вторым.

Отказы при этом двух родов, и путать их нельзя. «Смотреть не на что» — ресурс
не открылся, источник не описался: кадра нет вовсе, и заменить его может только
причина. «Кадр неполон» — сорвался проход, отказал кэш: ступени выше уже
нарисованы, снимок виден, и стереть его ради одного оборванного чтения было бы
неправдой — причина уходит подписью в полосу состояния и снимается первым же
приехавшим тайлом (`ViewState.error` и `ViewState.trouble`).

**«Работа идёт» — три факта, а не один** (`tiles::working`), и каждый ловит то,
что пропускают двое других: заказанные ячейки в полёте; идущий по источнику
проход — чей угодно, потому что свои ячейки он добудет заодно; и непройденный
путь к цели. Последнее не выводится из первых двух: ступень, набранная целиком
из кэша, не поднимает ни одного прохода и не держит ни одной ячейки в полёте, —
а следующая за ней пойдёт немедленно, без единого движения камеры, и объявить в
этот миг работу конченой значит сказать «загрузка кончилась» посреди загрузки.

**Пирамида набирается сверху вниз, а не прыжком к нужному уровню.** Спрашивают
самую грубую ступень, которой не хватает: вершина — это один тайл из самой
мелкой копии файла, он приезжает за секунду и накрывает снимок целиком, тогда
как нужный уровень из десятка тайлов по мегабайту едет полминуты, и всё это
время показывать было бы нечего. Каждая добытая ступень становится предком для
следующей, поэтому дыр между ними не бывает: ячейка рисуется точным тайлом, а
пока его нет — куском ближайшего имеющегося предка (`tiles::Store::carrier`).
Правило одно на обоих потребителей (`tiles::want`): ступень просят, её же и
рисуют.

**По скольким ступеням идти, решает цена прохода у источника.** Она приезжает в
описании (`Described.reach`) и отвечает на один вопрос: во что обходится лишняя
ступень. Точечному чтению (COG) — в свои тайлы, и не больше; проходу, который
строит всю пирамиду разом (PNG, полосный TIFF, мелочь), — вообще ни во что:
первая же ступень оплачивает остальные, дальше они попадания в кэш. А вот у
JPEG и JPEG 2000 проход строит только запрошенный уровень и грубее, за
подробным приходят заново, — там каждая ступень стоит ещё одного чтения файла
целиком, и лестница умножала бы цену на число ступеней. У таких источников
ступеней две: вершина, чтобы снимок появился, и сразу цель.

Кэш тайлов — `runtime/data/tiles/<отпечаток>/` (в `.gitignore`). Отпечаток
выводится из байтов источника плюс сторона тайла и ревизия правил
декодирования (`<fnv64>-t<сторона>q<ревизия>`), поэтому «смотрел по сети → скачал»
продолжает жить на одной пирамиде, а повторный показ не зовёт ни сеть, ни
декодер. Правка правил показа — растяга, ключевания nodata, взвешивания
ужатия — двигает ревизию, и старые каталоги кэша стареют до вытеснения:
версий и миграций у него нет.

Читаются источники тремя путями. Формат с произвольным доступом (тайловый TIFF
с обзорами — COG) отдаёт запрошенные тайлы точечным чтением чанков. PNG,
полосный TIFF, NetCDF и мелочь (GIF, BMP, WebP) читаются одним последовательным
проходом от нулевого уровня, который строит и складывает в кэш все уровни
разом. JPEG и JPEG 2000 декодируются сразу в масштаб запрошенного уровня и
каскадируют вниз от него — уровни крупнее приезжают отдельным запросом.

Форматы: PNG, JPEG, GIF, BMP, WebP; JPEG 2000 (квиклуки и гранулы
Sentinel-2 — декод сразу в масштаб уровня; насколько подробный уровень влезает
в бюджет памяти декодера, сказано в описании источника (`Described.finest`), и
подробнее него у тайлера не просят вовсе; поля гранулы — нули, примыкающие к
краю кадра, — прозрачны, внутренний настоящий чёрный не трогается); TIFF —
полосный и тайловый, BigTIFF, многостраничный (обзоры COG), сжатия — те, что включены фичами крейта `tiff` в
`image-tiler/config.yaml` (none/LZW/Deflate/PackBits/JPEG/Fax, плюс Zstd для
measurement-COG Sentinel-1; C-шный zstd-sys собирается в wasm — см.
`wasm_cc_env` в build.py), и двигаются они правкой этой строки, а не кода, сэмплы u8, u16,
i16 и f32 (DEM, амплитуда SAR); многополосный без цветовой интерпретации — это
не отказ, а стопка измеренных величин, и показывается первая из них
(`radiometry::Pixel::stack`): так GDAL пишет любой стек полос, и вторая полоса
в нём не прозрачность, хотя сэмплов у пикселя, как у серого с альфой, ровно
два. Разрядность меньше байта отвергается при описании: сэмплы такой глубины
крейт отдаёт упакованными, по нескольку в байте, а сборка тайла считает их
целыми — отказ здесь честнее, чем выход за границу буфера посреди прохода.
Широкие сэмплы растягиваются в байты по
перцентилям [2%, 98%] выборки самого файла — правило показа, а не радиометрия
данных, — и объявленное тегом GDAL_NODATA значение становится прозрачностью;
цветовые модели Gray/RGB/RGBA. Годен ли отсчёт (число ли он и не метка ли «нет
данных»), решает один предикат на всех, кто об этом спрашивает
(`radiometry::is_data`): выборку растяга и показ разводить нельзя — значение,
выброшенное из выборки как негодное, вышло бы на экран непрозрачным и, будучи
выше верхнего края растяга, белым. Ровное поле — то, у которого перцентили
совпали, — встаёт в середину шкалы, а не в её нижний край: чёрный кадр
неотличим от пустоты, а раздвигается интервал от величины самого значения, а не
на единицу (у f32 за 2²⁴ единица теряется, а такие числа как раз и стоя́т
метками «нет данных»). Прозрачное не подмешивается в цвет: усреднение
при ужатии взвешено по альфе (`resample.rs`), а под самим прозрачным пикселем
лежит не чернота, а цвет ближайшего непрозрачного соседа
(`adapters::bleed_alpha`) — иначе линейная фильтрация даёт по кромке `nodata`
тёмный ореол, который ячейка, нарисованная предком, растягивает вдвое на каждую
ступень. Честной ошибкой
отвечают: f16/f64, u32/u64, разрядность меньше байта, палитровые/CMYK/YCbCr,
планарная раскладка. Сжатие, фичей не включённое (WebP-in-TIFF), отвергает сам
крейт — своей ветки под это у адаптера нет.

**NetCDF-4 — не картинка, а набор измеренных величин** (`adapters/netcdf.rs`;
Sentinel-5P, Sentinel-1 OCN, гранулы Sentinel-3, климатика). Внутри лежат
температура поверхности, содержание газа в столбе воздуха, качество измерения,
точность измерения, время съёмки, углы наблюдения — и показать такой файл
значит выбрать из них ту, которая и есть измерение. Правила выбора — CF, то
есть те же, которыми файл описывает себя сам, шаблонов имён миссий здесь нет.

Сперва отсев по заголовкам: величина двумерна (единичные оси не в счёт), не
названа чужими `coordinates` или `ancillary_variables` (это «где» и «насколько
точно», а не «что»), не размечена `flag_values` (код состояния, а не
измерение), и сама не «где» и не «когда» — единицы широты, долготы и времени
исключают её (`degrees_north`, `degrees_east`, `seconds`, `microseconds`;
время — по первому слову единиц, иначе `m s-1` читалось бы секундами).

Оставшиеся выстраиваются в порядок предпочтения: ближе к корню (подробности
расчёта лежат в подгруппах), дробная прежде целой (целое в CF — счётчик, код,
индекс), не угловая прежде угловой (замкнутый угол в яркость не растягивается:
359° и 1° — соседи, а перцентили разводят их по краям шкалы), а дальше по
алфавиту — не выбор, а определённость.

**А выбирает из этого порядка чтение, а не заголовок.** Величина, у которой не
оказалось ни одного годного отсчёта, — не изображение этой гранулы: SLSTR
несёт величины, снятые не над всякой поверхностью («только над океаном»), и над
сушей такая лежит сплошным `_FillValue`. Показанная, она даёт прозрачный кадр
без единого слова о том, почему на шаре ничего нет, — поэтому пустая
пропускается, а однотонная берётся последней, если ничего лучше в файле не
нашлось. Проб столько, сколько влезает в тот же потолок, что у одной величины
(`PROBE_BUDGET`): считать их числом нельзя — у гранулы SLSTR плоскость 157×126,
а у полосы Sentinel-5P одна плоскость стои́т мегабайтов. Прочитанное остаётся
показу, поэтому второго чтения файла не случается. Не нашлось ни одной
заполненной — это ответ, и он называет, чего именно не нашлось.

В яркость значения переводит тот же перцентильный растяг, что у широких сэмплов
TIFF, `_FillValue` — в прозрачность. Годность отсчёта при этом решает один
предикат на всех (`radiometry::is_data`): выборка растяга и сам показ спрашивают
об этом одно и то же, а разойдясь, они дают белый непрозрачный пиксель там, где
выборка сочла значение негодным. Ровное поле встаёт в середину шкалы, а не в её
нижний край: чёрный кадр неотличим от пустоты.

Привязка приезжает из самого файла двумя путями. Полоса съёмки несёт широту и
долготу поотсчётно: называет их либо сама (`coordinates`), либо — когда
CF-атрибута в упаковке нет вовсе, как в `.nc` внутри `.SAFE`, — тем, что в её
группе лежит ровно одна плоскость той же формы в `degrees_north` и ровно одна в
`degrees_east`. Единственность обязательна: две широты одной формы — это уже
вопрос «которая», а ответа на него у файла нет. Регулярная сетка вместо этого
несёт две оси, и узнаются они по тем же единицам и по длине. И то, и другое
сводится к решётке опорных точек 21×21 — той же, какой пользуется радарный
снимок.

Читается такой файл целиком, и это не лень: HDF5 раскладывает величину чанками
по всему файлу, а каталог чанков лежит там же вперемешку с ними — «только нужное
окно» не прочитать, не прочитав половину файла окольными запросами. Отсюда
потолок в 96 МБ на файл: чтение идёт по сети, у CDSE это порядка полутора
мегабайт в секунду, и минуты ожидания довольно. Спектральный куб Sentinel-5P
уровня 1B (118–697 МБ) отвергается этим потолком, и это правильный ответ: полос
радиометра там четыре сотни на пиксель, изображения среди них нет.

### Наложение на глобус

«На глобус» ведёт продукт тем же конвейером тайлов, что и превью, — вторым
потребителем, а не вторым путём. Разделение то же, что у контуров: провайдер
знает раскладку продукта (`on_imagery` — роли растров: превью и подробный — и
рамка гранулы в метрах её зоны UTM, выведенная из MGRS-кода в имени тайла),
глобус умеет натянуть открытые ресурсы на привязку (`on_overlay`, набор
целиком; ресурсы приходят во владение), а сводит одно с другим `data-browser`.

Чем открывать каждый растр, решается по нему самому, а не по снимку: скачанный
целиком открывает библиотека — файл под рукой, и ходить за ним по сети значит
ждать того, что уже есть, — остальное открывает провайдер. По растру, потому
что у продукта скачана бывает часть: лежащий рядом квиклук не делает локальным
измерительный растр. Правило одно и общее с просмотром строки
(`LibraryState::local_name`).

**Какой файл продукта показывать, говорит сам продукт.** В корне всякого
`.SAFE` и `.SEN3` лежит манифест XFDU (`manifest.safe`, `xfdumanifest.xml`), и
это не метаданные про съёмку, а опись пакета: единица рода «Measurement Data
Unit» указывает на объект, а объект называет файл. Провайдер спрашивает его
вторым ходом после обхода поддерева (`manifest.rs`, `Asked::Manifest`) — один
запрос на 20–300 КБ, — и названным сужает выбор подробного растра. Без
манифеста выбирать пришлось бы по именам файлов, а это гадание ошибается там,
где ошибиться дороже всего: у гранулы SLSTR `LST_ancillary_ds.nc` стои́т в
алфавите раньше `LST_in.nc`. Не достался или ничего не назвал — разбор
возвращается к именам, как и было до него.

Имена решают в трёх узнаваемых раскладках и в общем случае. Гранула Sentinel-2
(квиклук из QI_DATA и истинный цвет из IMG_DATA), гранула Sentinel-1 (квиклук
из preview и measurement-COG), продукт одним объектом (сам себе растр — им
лежит климатика) и общая: обзорная картинка отдельно, подробным — то, что
похоже на цветной снимок целиком, иначе первое по алфавиту. Подкаталог
`preview/` подробного растра не даёт вовсе: это часть раскладки, и сказано в
ней то же, что словом — внутри обзорная картинка, шкала прибора, логотип
миссии. «Цветной снимок целиком» узнаётся по слову, а не по куску: подстрокой
«TCI» ловится `otci.nc`, индекс хлорофилла OLCI.

**«Показывать нечего» — это ответ, и он объясняется.** Растров в продукте не
находится по-разному: продукт лежит одним архивом (архив калибровочных таблиц
`.TGZ`) — такой и листать нечем, ответ приходит без единого запроса к
хранилищу; продукт — сырьё уровня 0, где изображения ещё нет вовсе, только эхо
приёмника; продукт снят миссией, чью раскладку мы не разбираем, и растр в нём
есть. Поступают с этим по-разному, а «нет растров для наложения» одинаково для
всех, поэтому провайдер называет причину словами и перечисляет, что в продукте
лежит (`ImageryResponse.reason`, `imagery::nothing_here`). Отдельно от `error`:
«спросить не вышло» стоит переспросить, «показывать нечего» — нет.

Снимков на шаре несколько, и они лежат стопкой: порядок набора — порядок слоёв
снизу вверх, у каждого своя прозрачность и своё «скрыт». Всё это едет в том же
`on_overlay`: **другого способа сказать глобусу про наложения нет**, поэтому
всякое изменение — добавление, снятие, движение ползунка — кончается отправкой
набора целиком. Растры при этом пересылаются прежними дескрипторами, и глобус
по ним узнаёт, что наложение прежнее: движение ползунка ничего не
переоткрывает. Скрытый слой остаётся в наборе вместе с ресурсами, но не
рисуется и тайлов не просит — тем и отличается от снятого, что вернуть его
обратно значит ничего не открывать заново. Потолок аппетита тайлов делится
между всеми пирамидами, которые сейчас рисуются: уровень целиком, взятый
каждой, вымывал бы соседей. Пирамидами, а не слоями — у слоя их до двух,
превью и подробная, и лежат в бюджете обе.

**Хочет наложение только то, что видно.** Ячейки выбранного уровня
проверяются на попадание в кадр той же матрицей, которой кадр и рисуется:
девять точек ячейки — углы, середины сторон и центр — переводятся привязкой в
точки мира и проецируются, а дальняя сторона Земли отсеивается тем, что все
девять отвёрнуты от глаза.

Ответ этот дорог: обратный ход привязки стоит по шесть десятков
трансцендентных вызовов на пробу, а ячеек у подробного растра под две тысячи на
уровень, и спрашивают их каждый кадр движения камеры. Поэтому перед ним стои́т
грубый отсев: ячейка накрыта шаром, шар проверяется против четырёх боковых
плоскостей кадра и против горизонта — три десятка сложений и ни одного
трансцендентного вызова. Сказавшему «не видно» верят; сказавшему «видно» —
нет, и приговор выносят те же девять проб. Шары считаются раз на описание
растра: от привязки и размеров они зависят, а от взгляда не зависят вовсе.
Пробуется при этом только нулевой уровень, а верхние получаются слиянием
четвёрок — ячейка родителя есть в точности объединение её детей, — и запас,
которым пробам прощается непроверенное между ними, живёт тогда лишь там, где
ячейка занимает пятьсот двенадцать пикселей и привязка внутри неё почти
билинейна.

Запас этот у шара и у точного теста один и тот же, и это не удобство: шар
обязан не отвергать признанного точным тестом, а тот признаёт ровно на радиус
покрытия дальше своих проб. Две мерки одного и того же разошлись бы молча —
ячейками, пропавшими у самого лимба.

Отвёрнутость эта — вопрос о ячейке, а не о точке, и потому спрашивается с
запасом. Между пробами лежит непроверенное, а ячейка бывает крупнее видимого
куска Земли на четыре порядка: у вершины глобального растра девять проб
вырождаются в четыре точки — два полюса и две на экваторе, — и над серединой
между ними все четыре лежат ровно за горизонтом. Без запаса такой слой не
показывался бы ни с какой высоты вовсе, а пропажу нечем было бы и заметить:
ячеек не осталось, значит и тайлов не заказано, значит доля хода — единица,
«готово» над пустым шаром. Запас равен радиусу покрытия сетки проб —
половине самого длинного её шага по диагонали, — и меряется он градусами:
хорда между углами у той же вершины назвала бы вдвое меньше, чем нужно. Уровень при этом
грубеет, пока видимого не станет меньше потолка, и мерить потолком уровень
целиком нельзя: гранула 10 000² целым нулевым уровнем не влезает ни в какой
бюджет, и снимок не показал бы подробностей ни на каком приближении, — а видно
от силы десяток ячеек, сколько ни приближай. К выбранному уровню при этом идут
ступенями от вершины пирамиды (см. «Поток просмотра»), и спрашивается ступень:
считает это одна функция на обоих спрашивающих
(`Overlay::wanted`) — заказанное обязано быть тем же, что рисуют, а нарисованная
ячейка — той, которую просили. Одна функция, а не одно вычисление: зовут её и
отсев промахов, и заказ тайлов, и сборка патчей, а сходятся они на том, что
довод у неё один и тот же.

**Ход добычи виден в списке.** По самому шару его не видно — снимок либо уже
нарисован, либо ещё нет, — а ждать бывает десятками секунд, и «нажал и ничего не
произошло» выглядит поломкой. Поэтому глобус рассылает `on_overlay_progress`:
набор целиком, по строке на наложение, и только когда он изменился. «На
просмотре» показывает его подписью («тайлы 3/9»), а строка того списка, из
которого снимок отправили, — полосой под собой. Высота полосы у строки занятая,
а не добавленная: шаг строки считается в одном месте, и по нему список
прокручивают к нужной строке. Занята она, пока снимок на шаре, а не пока по нему
идёт работа, — иначе строка подпрыгивала бы на три точки ровно в тот миг, когда
добыча кончилась.

**Ход меряется заказом, а не кадром.** Доля, которой рисуется полоса, — это
ступени пирамиды: от вершины, с которой начинают, до уровня, на котором картинка
станет резкой. Ступеней у слоя столько, сколько их есть, и каждая закрывается
один раз, поэтому панорама долю не двигает; приближение двигает, и это правда о
работе — подробнее нужный уровень значит длиннее путь. Внутри ступени доля
берётся по большему из двух: сколько ячеек последнего **заказа** уже дома и
сколько байт источника прочитал идущий проход. Второе не роскошь: ступень бывает
в один тайл, а чтобы его отдать, последовательный источник читается целиком —
по ячейкам всё это время сделано ровно ноль. Числа же в подписи («тайлы 3/9») —
про тот же заказ, а не про то, что попало в кадр: видимое есть функция камеры, и
счёт, выведенный из него, менялся бы на каждом кадре жеста, ничего не сообщая.

**«Работа идёт, а доли нет» — отдельный ответ, а не ноль.** Пока растр
описывают, считать в слое нечего: ячеек не заказано, ступеней не насчитано. У
растра, лежащего по сети, это самая долгая часть пути — десятки секунд, — и
записанная нулём она рисуется пустой дорожкой в три точки, то есть никак.
Поэтому глобус говорит о ней отдельным полем (`OverlayProgress.blank`): ответить
на «уже видно хоть что-нибудь» может только он — снаружи «лежит на шаре» и
«виден на шаре» неразличимы. По нему приславший и рисует полосу без доли —
заливая всю дорожку вполсилы, — и им же гасит штриховку, которой помечено место
снимка. Вывести это из чисел нельзя: доля бывает нулевой и у честно
начатой ступени, а у пирамиды в один уровень ступеней ноль и тогда, когда
картинка давно на месте.

Описание при этом считается работой независимо от кадра: слою, которому не дают
считать (скрыт, места под кадр нет), добывать нечего — а описание уже в полёте и
кончится само. Объявленное стоящим, оно оставляло бы нажавшего значок без
единого признака работы ровно на те секунды, когда признак нужнее всего.

**«Не ляжет» — тоже ответ, и он едет тем же топиком.** Заметить, что слою
негде лежать (нет привязки, ни один растр не открылся, ни один не описался),
может только глобус — у него растры и привязка. Убрать такой слой может только
приславший — набор наложений принадлежит ему. Поэтому причина уезжает полем
`error` в том же ходе добычи, а `data-browser` снимает слой и говорит почему —
тем же путём, что и собственные отказы сборки: пустая строка, которая никогда
ничего не покажет, хуже её отсутствия.

**А «резче не станет» — ответ другой, и поле у него своё.** Растров у наложения
два, и отказавший один оставляет слой жить вторым: снимок на шаре есть, просто
подробного у него не будет никогда. Убивать за это слой нельзя, но и молчать
нельзя — приблизившийся ждёт резкости, а по пустой подписи «ещё едет» от «не
будет» не отличить. Причина едет полем `trouble` того же хода добычи и
показывается подписью рядом с полосой, когда сама работа кончилась. Разделение
то же и по той же причине, что у канвы (`ViewState.error` против
`ViewState.trouble`).

**Значок глобуса горит, когда снимок на шаре.** Зелёный — лежит растром и виден,
вполсилы — лежит, но увидеть его сейчас нельзя (едет или скрыт), обычный — его
там нет. Так по строке видно, лежит ли снимок растром, и считается оно в одном
месте на все три списка (`components::rows::onto_globe`): шар один, а списков
сколько угодно, и три выражения по месту разошлись бы молча. Тем же местом
считается и полоса под строкой, и штриховка занятой области — вопрос у всех
троих один, «что с этим снимком на шаре сейчас». Отсюда же и подпись значка — она
называет то, что случится по нажатию, а не то, что есть: у лежащего это снятие,
а не второе наложение.

Стоит он в строке всякого снимка — в поиске, в сетевом каталоге и в
скачанном; у строки, снимком не являющейся, то же действие остаётся пунктом
меню. У
найденного продукт с футпринтом уже под рукой; у строки каталога или файла на
диске есть только ключ, и продукт по нему восстанавливает провайдер
(`on_locate`: подъём от ключа к корню продукта — раскладка бакета, дальше
каталог по точному имени). Чем накрыт шар, показывает вкладка «На просмотре»:
там же слои гасят ползунком, скрывают, убирают и переставляют, оттуда же
уходят к самому снимку — смотреть его и находить в каталоге. Показано там всё,
что на шаре, а не одни растры: снимок бывает на нём и одним контуром, и убрать
его иначе можно было бы только вернувшись в список, к значку контура. Обратный ход есть
и в полосе вкладки глобуса: она называет выбранный снимок, ведёт к нему теми же
двумя переходами, а «Снять с шара» убирает всё разом — и растры, и контуры.
Названный снимок вытесняет из полосы и размер области, и подсказку про
управление: имя занимает весь остаток полосы, а место кнопкам разметка отводит
первым — в панели вполовину экрана иначе за край уезжают как раз они.
Наложение из выдачи поиска живёт её жизнью — уходит с продуктом из выдачи и с
закрытием вкладки; показанное по ключу от выдач не зависит и снимается только
руками.

Снимок, лежащий каталогом, качается целиком: список его файлов приезжает
рекурсивным листингом (`ListPathRequest.recursive`), и каждый уходит в
библиотеку своей закачкой — снимка она не знает вовсе, её предмет файл.
Доведённое при этом пропускается: перекачка сносит готовый файл до старта, и
«докачать снимок» стирало бы ровно то, что в нём уже есть. Перекачивают по
одному файлу, из его меню, где это и помечено необратимым. Останавливается
снимок тем же разворотом, каким качается: «приостановить снимок» в его строке
«Скачанного» жмёт паузу каждому идущему файлу — по одному их у снимка под три
десятка.
Раскрыть такой снимок можно и не уходя со списка: треугольник у строки листает
её содержимое и показывает подстроками, вглубь на сколько угодно ярусов. Внутрь
при этом по-прежнему заходят нажатием на саму строку, поэтому отдельной стрелки
перехода рядом с ней нет.

Рисуется наложение варп-сеткой: ячейка тайла бьётся на квады, узлы считаются
привязкой, UV — линейно по тайлу-носителю; растр не ресемплится вовсе,
искажение проекции берёт на себя сетка.

**Густота этой сетки выводится из того, сколько дуги занимает ячейка**, а не
назначена числом. Квад — плоский четырёхугольник на четырёх точках поверхности,
и середина его проваливается под неё на `R·(1−cos(θ/2))`: у гранулы это метры,
а у ячейки верхней ступени глобального растра — сотни километров. Тело Земли
пишет глубину, наложение с ней только сравнивается, и провалившееся не рисуется
вовсе — снимок во всю Землю был бы виден клочками у самых узлов сетки. Поэтому
звено делят, пока его провал не уложится под общий вынос, а чего не добрало
деление — у ячейки в 360° звеньев пришлось бы больше девятисот, — добирает
высота: остаточный провал считается тут же и поднимает узлы ровно на него.
Соседям подъём не мешает: контуры и сетка рисуются позже наложений и глубину не
пишут.

**Вынос над поверхностью один на всё, что на ней лежит** — на снимки, контуры,
штриховку, сетку и на ответ о том, куда пришёлся щелчок (`mesh::SURFACE_LIFT_M`,
восемьдесят метров). Один он не ради порядка слоёв: порядок решает очередь
отрисовки, а глубину пишет только тело Земли. Один он ради места на экране —
точка на высоте `L` при камере на высоте `H` отходит от середины кадра в
`H/(H−L)` раз, и слои, разнесённые по высоте, расходятся на экране тем сильнее,
чем ближе к краю кадра. Разнеси контур со снимком на километр, и у кромки кадра
обвод разойдётся со своим снимком на полкилометра по земле. Поэтому каждый
носитель делит себя до предельной хорды и садится на общий вынос; поднимается
над ним только тот, кто упёрся в свой потолок густоты, и ровно на остаток
своего провала.

Тем же выносом отвечает и `on_probe`: луч встречает не эллипсоид, а поднятую
поверхность, потому что под курсором видно нарисованное, а нарисовано оно там.
Иначе щелчок называл бы место, отстоящее от увиденного, — тем дальше, чем ближе
к краю кадра.

**Привязок четыре, и старшие — те, что лежат в самом растре.** GeoTIFF несёт
решётку опорных точек (`ModelTiepoint`; у гранулы Sentinel-1 это 21×21 узел в
градусах) либо матрицу (`ModelTransformation` — ею пишется повёрнутый растр,
шаг по осям такого не задаёт), NetCDF — поотсчётные широту с долготой или две
оси сетки, из которых тайлер собирает такую же решётку; отдаёт он её вместе с
описанием (`Described.ties`) — она единственная говорит не «какой кусок Земли
снят», а «каким пикселем куда».

У Sentinel-3 та же привязка лежит **в соседнем файле**: в измерительном `.nc`
одна полоса чисел, а широта с долготой — в `tie_geo_coordinates.nc`
(`geo_coordinates.nc`) у OLCI и в `geodetic_<сетка>.nc` у SLSTR. Поэтому растр
приезжает к тайлеру вторым ресурсом: какой это файл, знает провайдер
(раскладка продукта — его дело), владеет им глобус наравне с самим растром, а
тайлер спрашивает его только тогда, когда в растре опорных точек не нашлось.
Сетка координат бывает разрежена — у OLCI опорная вчетверо у́же снимка, — и шаг
выводится из размеров: крайние отсчёты сетки стоят на крайних пикселях растра.
Координаты при этом **разупаковываются** (`scale_factor`, `add_offset`): у
Sentinel-3 широта записана целыми с шагом в миллионную долю градуса, и без
этого получаются не градусы, а десятки миллионов. Показываемой величине те же
коэффициенты не нужны — растяг считается по перцентилям тех же значений.

Рядом с решёткой стои́т вторая привязка из файла: растр может лежать **не в
градусах, а в метрах проекции** — так пишут Landsat и всё, что нарезано в UTM.
Тайлер отдаёт её сырьём (`Described.placement`): код EPSG и шестёрка чисел,
которой пиксель переводится в метры системы. Толковать код он не может и не
должен — проекционная математика в дереве одна (`globe/src/projection.rs`), и
вторая её копия сошлась бы с первой на глаз и разошлась на числах; вдобавок
глобус уже зависит от тайлера, и обратная зависимость дала бы цикл. Поэтому код
разбирает глобус (`System::from_epsg`), а шестёрка ложится в рамку как есть.
Код, которого он не знает, не выдумывается: строка в логе называет его, и
привязка остаётся по контуру.

**Система координат — это параметры, а не имя.** UTM, шестиградусные зоны
Гаусса-Крюгера и местные системы вроде МСК-61 — одна и та же поперечная
цилиндрическая проекция с разными числами: масштабом на осевом меридиане (у UTM
0,9996, у остальных ровно единица), самим меридианом, сдвигами и тем
эллипсоидом, к которому отнесены градусы. Зашитый UTM пришлось бы переписывать
под каждую следующую систему, а число — просто другое число.

Датум при этом не менее важен проекции: СК-42 стои́т на эллипсоиде Красовского,
и принятая за WGS84 она уводит точку в Ростовской области на **112 метров**.
Почти всё это — сдвиг центра эллипсоида, а не его форма: подменить один
эллипсоид другим и на том успокоиться значит убрать два метра из ста
двенадцати. Поэтому переход считается семью элементами Гельмерта (ГОСТ Р
51794-2008 — тот набор, которым описаны местные системы в приказах, по которым
ведётся кадастр; более поздний из ГОСТ 32453-2017 отличается на двадцать
сантиметров). Делается он **внутри** `projection.rs`, потому что снаружи его
негде сделать честно: широта на Красовском и широта на WGS84 выглядят
одинаково, и перепутанные, они расходятся молча. Наружу отсюда уезжает только
WGS84.

Проверяется всё это четырьмя узлами, сошедшимися со сторонним пересчётчиком:
узлы МСК-61 зон 1, 2 и 3 ложатся там же, где их кладёт geobridge, — **с
точностью до полумиллиметра**. Порознь ни эллипсоид, ни ряды, ни отступы зоны,
ни семь элементов не проверяемы; сойдясь, они проверяют друг друга.

Пара «прямая и обратная» у датума точная только в геоцентрике. В градусах
остаётся остаток: Гельмерт разворачивает и вертикаль, а высоту привязка растра
не несёт — наружу уезжают два числа из трёх. Там, где датум и подгонялся, это
микроны; за тысячи километров от него — миллиметры.

Шестёркой, а не парой «начало и шаг», потому что ею выражается и повёрнутый
растр; прямоугольник по осям — её частный случай с нулями вне диагонали, и
отдельного вида рамки для него нет. Точность у такой привязки не
интерполяционная, а настоящая: перевод считается **на каждом узле варп-сетки**,
а не между углами. Между углами он бы и не сошёлся — линия постоянного северного
отступа не есть линия постоянной широты, и на сцене Landsat 239 км под 69°
середина верхнего ребра отстоит от дуги между углами на два десятка метров, а на
грануле в 110 км под 60°, взятая прямой в градусах, — на четыре сотни.

Ниже них рамка UTM от провайдера, выведенная из
MGRS-кода в имени тайла: точная, но только у гранул Sentinel-2 — у прочих такого
кода в имени нет. Она того же вида, что и привязка из файла, и потому уступает
ей по роду, а не по приходу: файл знает свою раскладку, а имя лишь обещает её
(`overlay::Binding`). Ниже всех — четырёхугольник футпринта из каталога:
он отвечает на другой вопрос, и порядок его вершин обходу растра не обязан
совпадать — прочитанный обходом, он кладёт снимок радара повёрнутым на четверть
оборота.

Долготы решётки разворачиваются вдоль неё самой, а не к первому узлу: сетка
глобального растра идёт на все 360°, и разворот к одной вершине сложил бы её в
меридиан. Соседние узлы стоят в десятках километров друг от друга, и разница
между ними больше полукруга не бывает — шов между ними виден однозначно.

**А контур сложнее четырёхугольника — это не привязка и не догадка.** Полоса
съёмки Sentinel-5P очерчена семью десятками вершин; натянуть растр на её габарит
значит показать его вдвое шире снятого и не под тем углом. Такой снимок кладётся
местом (`Frame::Rough`): по этому месту не рисуется и не просится ничего, оно
лишь держит слой, пока привязку не принесёт сам растр. Не принёс — наложение не
состоялось, и слой кончается ошибкой. Отказывать раньше, на контуре, было бы
рано: привязка живёт в растре чаще, чем в каталоге, а спросить растр можно
только открыв его.

**Ребро ведут так, как его назвали.** Совпали широты его концов — это
параллель; совпали долготы — меридиан; прочее — кратчайшая дуга
(`geodesy::edge_point`). Правило одно на всех, кто ходит между **углами**:
на четырёхугольник футпринта, на уплотнение контуров и на попадание щелчком.
Решётка опорных точек идёт своим ходом, и это осознанно: узлы у неё стоят в
двух десятках километров, где дуга с прямой расходятся на метры, а не на
километры, и своих сложностей там хватает на отдельную работу.
Иначе контур снимка висел бы в стороне от собственного снимка: у клетки в
градус на шестидесятой широте дуга уводит середину ребра на сотню метров от
параллели, у ребра в двадцать градусов — на сорок километров.

Разбор нужен потому, что права бывает и та, и другая. Прямая в широте с
долготой — это локсодрома, путь постоянного азимута, и на высоких широтах она
заметно расходится с кратчайшим, которым спутник ведёт край съёмки: у верхнего
ребра гранулы EW GRDM (421 км на 73° с. ш.) середина дуги отстоит от середины
«в градусах» на 13 км, и отход растёт как квадрат длины ребра. А клетка
географической сетки — рельеф Copernicus и всё, что записано градусами, — идёт
ровно по параллелям, и вести её дугой значило бы сдвинуть снимок ровно на ту же
величину, только в другую сторону. Различает их не вкус, а то, чем ребро
записано: у клетки широты концов равны, у полосы съёмки — нет.

Плата у правила одна, и она названа: род ребра решается совпадением координат, а
каталог отдаёт их округлёнными. Сойдись широты двух углов случайно — и полоса
съёмки ляжет параллелью вместо дуги. Зато ляжет так же, как её обведут и как по
ней попадут щелчком: обводка со щелчком читали футпринт одним правилом и
прежде, а растр — своим, и расходился с ними он один. Совпадут они при этом не
тождественно: кольцо контура уплотняется вчетверо реже варп-сетки растра, и его
звенья выгибаются сами — на клетке в градус остаётся два с половиной десятка
метров из прежних ста пяти. Поэтому наложение, висящее на
квадре, до конца описания растров не рисуется и тайлов не просит: нарисованное
по догадке пришлось бы через секунду повернуть на глазах, а спрошенное —
выбросить, потому что видимость ячейки считается той же привязкой. Решётка ещё
и точнее по существу: снимок в геометрии съёмки четырьмя углами не описывается,
кривизна набегает километрами, и соседние гранулы одного витка сходятся в
сплошную полосу только по ней. Обратная проекция UTM → широта/долгота → мир
живёт там же, где прямая (`globe/src/projection.rs`, пара с тестом сходимости).

Насколько подробный уровень вообще достижим, решает не пирамида, а пол высоты
камеры (`camera::HEIGHT_RANGE_M`): с высоты `h` **над нарисованным** в кадре
умещается по вертикали `0,93·h` метров поверхности — при окне в тысячу строк это
`h/1070` метров на пиксель. Пол — восемь сотен метров, из которых восемьдесят
съедает вынос, то есть семь десятых метра на пиксель: подробнее любого снимка,
какой сюда приезжает, и довольно, чтобы вести границу поля рукой.

**Выведен он из выноса, а не назначен числом.** Спуститься к выносу вплотную
значит пройти сквозь нарисованное, и десятикратный запас — то, при котором вынос
ещё не мешает ни ближней плоскости, ни перспективе. Искажения вынос при этом не
даёт: он смещение, а не увеличение, и всё, что меряет камеру над видимым, меряет
до него (`mesh::drawn_radius`). Мерка до эллипсоида ошибалась бы во столько раз,
во сколько высота больше высоты за вычетом выноса, — на десяти километрах это
восемь десятых процента, а на восьмистах метрах уже одиннадцать.

Точность координат полу не указ. Позиция уезжает в шейдер **половинами**, и шаг
её идёт от расстояния до глаза, а не от радиуса Земли: у пола это десятки
микрон, тогда как одним `f32` было бы восемьдесят сантиметров при любой высоте
(`geodesy::parts`).

Уровень выбирается по метрам на экранный пиксель; превью-база рисуется всегда
и первой, подробные тайлы накрывают её по мере прихода — снимок виден сразу,
одним мелким файлом, а резкость приезжает следом. Бюджет видеопамяти у глобуса
свой (`vram_budget_mb`, 256 МиБ по умолчанию; в `globe.json` ключа нет, пока
его не понадобилось назвать), вытеснение — забывание: тайл остаётся на диске у
`tile-cache`.

**Вытесняется дольше всех не тронутое, и прикосновений три.** Приезд, показ в
кадре и показ потомка — всё это способы сказать «тайл в работе», и мерка у них
одна.

Приезд считается наравне с показом, хотя поставить только что приехавший тайл
впереди нарисованного выглядит осторожнее. Дело в том, что «нарисован» не
стареет: напанорамировав десяток экранов, хранилище набивается тайлами, которые
нарисованы когда-то и не нужны никому, — и в очереди они все стоят позади
приезжающих. Полное такими хранилище перестаёт принимать что-либо вовсе: первый
же приехавший тайл оказывается единственным «невиданным» и вытесняет сам себя,
следующий — себя, и заказ не складывается никогда. Снаружи это выглядит ровно
тем, чем является: снимок стои́т мутным, а сеть работает без остановки.

Показ потомка продлевает жизнь и предкам — всей ветке вверх, а не одному
носителю. Предок — это то, чем ячейку нарисуют, когда её точный тайл уедет, и
та же ступень, с которой пирамида набирается заново; продлевай мы жизнь одному
носителю, предки старились бы ровно с той минуты, когда их ступень достроилась
и трогать их перестали. Вытесненные, они превращают любую панораму в подъём от
вершины: снимок мутнеет на глазах и добирается ступенька за ступенькой, хотя ни
один лист не понадобился заново.

Что нарисованному при этом ничего не грозит, держит не порядок вытеснения, а
потолок аппетита: видимое вместе с заказом занимает меньше половины бюджета, а
тронуто оно позже всего прочего.

Поля nodata прозрачны — сквозь гранулу Sentinel-2 и снимок с тегом
GDAL_NODATA видна Земля. Без тега нули остаются цветом (чёрные клинья
GRD-COG): на отдельном тайле кромку от данных не отличить, а угадывать
тайлер не берётся. Предел детали — бюджет JP2-декодера: регионального декода
у hayro-jpeg2000 нет (только целевое разрешение), поэтому родной TCI 10980² за
бюджетом и ждёт декодера, который умеет читать кодопоток по тайлам. Предел этот
не отказ, а факт источника: он приезжает полем `Described.finest`, и цель
загрубляется до него ещё до того, как первый тайл будет спрошен, — иначе тот же
отказ переучивался бы на каждом сдвиге камеры и вылезал бы ошибкой в
интерфейсе.

```
data-browser  --on_download-->  data-library
data-library  --on_sign------>  data-provider   (подписать адрес)
data-provider --on_signed---->  data-library
data-library  --on_fs_download->  network       (владелец задачи — data-library)
network       --on_fs_download_progress-->  data-library
network       --on_fs_download_result---->  data-library
data-library  --on_state----->  data-browser
```

Разом идёт не больше десяти закачек (`download::AT_ONCE`), остальные ждут
места и трогаются, как только оно освободится, — в порядке нажатий. Потолок
нужен не нам, а той стороне: пакетное «скачать» на странице из двадцати снимков
— это сотни файлов за одно нажатие, и хранилище отвечает на такое отказами.
Ждущая запись видна в списке наравне с идущими — с тем, что у неё уже лежит на
диске, или с нулём у перекачки: с нажатия «скачать» она уже намерение
пользователя, и прятать её до старта значило бы терять нажатие из виду. Тем же
самым выглядит и окно ожидания подписи, оно и есть та же пауза, только короче.
Готовый файл перекачка при этом сносит в момент старта, а не нажатия: между
ними стои́т очередь, и снесённый заранее файл оставил бы человека без данных и
без закачки на всё время ожидания.

Остановок две, и различает их то, что остаётся на диске: `on_pause` бросает
`.part` точкой возобновления, `on_delete` не оставляет ничего. Обе убивают
операцию сама `data-library` — она её владелец, — и получают на это тот же
`on_fs_download_result`, только пустой.

Раскладку хранения знает только `data-library`; наружу уходят выведенные
записи каталога, без путей и служебных суффиксов. Держится это одним
инвариантом: **под одним именем на диске лежит один файл** — либо доведённый,
либо `.part`, но не оба. Иначе запись каталога выводилась бы дважды, а какая
из двух правд про неё показана, решал бы порядок обхода каталога. Нарушить
инвариант может только перекачка готового файла, поэтому она сносит его до
старта (`download::on_download`), а свёртка снимка по имени
(`catalog::on_list_result`) называет победителя даже для пары, положенной мимо
приложения.

Имя записи — не последний сегмент ключа, а путь: у файла из снимка это имя
снимка и путь внутри него (`S1_….SAFE/preview/quick-look.png`), и на диске он
так и лежит — снимок папкой. Иначе инвариант выше держался бы на удаче:
`quick-look.png` и `manifest.safe` есть в каждом продукте, и второй такой файл
означал бы не второй файл, а тот же самый — скачанный вторым сносил бы первый.
Каталог библиотеки поэтому читается вглубь (`FsListRequest.recursive`); сами
каталоги записями не являются и в ответе не приходят.

К какому снимку относится файл, библиотека не выводит, а запоминает: граница
снимка — раскладка хранилища провайдера (`s3::product_root`), приезжает она с
запросом закачки (`DownloadRequest.product`), переживает рестарт в сидкаре и
она же кладёт файл в папку снимка.
Свести файлы одного снимка в одну строку — уже дело показа: библиотека ведёт
учёт файлам, это её предмет, а «снимок» — то, чем их показывают
(см. `downloaded_rows`).

Целым снимок называется только по обходу. Сколько его файлов доведено, видно по
записям, а сколько их должно быть — нет: качали, может статься, три файла из
двадцати шести, и «на диске» у такого снимка означало бы «на диске всё, что
качали». Число это добывает тот, кто снимок качает — обход хранилища ему и так
нужен, чтобы поставить файлы в очередь, — и по концу обхода называет библиотеке
(`data_library/on_snapshot`), а та кладёт его в сидкары файлов снимка рядом с
`product`. Дальше показ сверяет доведённое с ним и в хранилище больше не
ходит: у снимка пропадает «скачать целиком», у строки — «N на диске»
(`LibraryEntry.siblings`). Оборванный обход числа не называет: перечисленное —
не весь снимок.

## Конфигурация

Конфиги лежат в `runtime/config/`:

| Файл | Назначение |
|---|---|
| `services.json` | каталог плагинов, путь к логам |
| `core.json` | фильтры логирования, подавление повторов |
| `<имя модуля>.json` | конфиг конкретного модуля |

Конфиг модуля ищется по имени, которое модуль сообщил через
`get_service_name`. Он целиком уезжает в `init` модуля и разбирается его типом
`Config`. Значения вида `${VAR}` подставляются из окружения; перед чтением конфигов
хост подхватывает `.env` (из текущего каталога или из корня проекта
относительно каталога конфигов), уже заданные переменные не переопределяются.
`plugins_dir` в `services.json` — тот же каталог, что в `workspace.yaml`;
сборка сверяет оба и падает с ошибкой при расхождении.

Ключ `window` в конфиге модуля объявляет окно:

```json
{
  "window": { "title": "VeldMap GIS", "width": 2048, "height": 1536, "ui_scale": 2.0 }
}
```

Фильтры логов — синтаксис `env_logger`, таргет записи имеет вид
`veldmap::<компонент>::<подсистема>`, где компонент — `host` или имя плагина.
`RUST_LOG` переопределяет `log_filter` из `core.json`.

## Добавление wasm-модуля

1. Создать `veldmodules/<имя>/` с файлами `schema.yaml` (`name:` совпадает с
   именем каталога) и `config.yaml` (имя пакета и зависимости Cargo).
2. При наличии собственных типов — добавить `types.proto`; на них ссылаются
   как `module/<Сообщение>`.
3. Написать `src/module.rs`: `Config`, `State`, `hook_init` и по функции на
   каждый топик из `interface.inputs` и `dependencies.*.subs`.
4. Добавить `runtime/config/<имя>.json`.
5. Собрать: `python3 buildgen/build.py`.

Модуль обнаруживается по наличию `schema.yaml` и `config.yaml`; порядок сборки
выводится из зависимостей в схемах. Регистрировать его где-либо ещё не нужно.

Модуль с собственным `types.proto` дополнительно получает wrap-крейт, через
который его типы видны потребителям. Рукописные хелперы для потребителей
кладутся в `wraps/rust/src/wrap.rs`; оттуда же можно включить файл самого
модуля (`#[path]`), чтобы производитель и потребитель считали одним кодом — так
живёт геодезия глобуса. Такой файл компилируется дважды, в двух разных крейтах,
поэтому нужные ему библиотеки объявляются и в `rust.dependencies`, и в
`rust.wrap_dependencies`: списки разные нарочно — иначе потребитель чужого API
тянул бы за собой всё, чем производитель пользуется у себя.

Из двойной сборки следует и правило видимости: **`pub` во включаемом файле
означает «видно и потребителям»**, а `pub(crate)` — «видно соседям по тому
крейту, который сейчас собирается», то есть в модуле соседним файлам, а в
wrap-крейте его собственным.

«Видно потребителям» — это при `pub mod` в `wrap.rs`; так включены пирамида
тайлера, геодезия глобуса и раскладка кэша. Типографика ui-service включена
приватным `mod`, а наружу её имена уезжают реэкспортом из `style.rs`: адрес
шрифта у клиента был там и там же остаётся, а второго у него не заводится.
Правило от этого не меняется — `pub` во включаемом файле обязателен и здесь:
`pub use` от `pub(crate)` компилятор не примет (E0364).

Отсюда и цена, которую приём берёт за единственный экземпляр: сузить молча
можно только то, до чего wrap-крейт всё-таки дотягивается. `FLATTENING` в
геодезии сужен и молчит — его зовёт публичный `intersect_at`. А `parts`, до
которого из публичных не добраться, сужением превращается в `warning: function
is never used`: в обёртке нет тех файлов модуля, что его зовут.

Обойти это можно двумя способами, и оба хуже. `#[allow(dead_code)]` глушит
предупреждение — и заодно ту единственную проверку, которой в дереве ловится
действительно мёртвое. Раскол файла на «общее» и «своё» вернул бы тишину, но
отменил бы то, ради чего включение и заведено: одна формула вместо двух,
сходящихся на глаз.

Поэтому лишняя публичность у геодезии — не небрежность, а плата: потребителю
оттуда нужна треть имён, а прочие держатся `pub` кто вынужденно (сузишь —
получишь предупреждение), кто просто по соседству. Разбирать их поимённо
незачем, важно правило: `pub` здесь не обещание «это API», а «сузить дороже,
чем оставить».

Сузив то, чем пользуется потребитель, автор упрётся в отказ — но не у себя, а
у чужого модуля; сборка в проекте одна на всё дерево, так что случится это в той
же команде, которой правку и проверяют. А вот `pub fn`, возвращающая
`pub(crate)`-тип, — только предупреждение (`private_interfaces`), и публичность
подписи тянет за собой публичность типов в ней скорее по соглашению, чем под
присмотром.

## Известные ограничения

- Область в запросе поиска задать **нечем в интерфейсе**, и не хватает для
  этого ровно рамки на шаре: контракт область принимает (`SearchRequest.area`),
  провайдер переводит её в `OData.CSC.Intersects`, обратный ход проекции есть
  (`globe/on_probe`), правая кнопка мыши до области доезжает и оставлена
  свободной именно под это (`handlers::globe::on_pointer`). Пока рамки нет, из
  экрана уходят миссия, часть имени, окно съёмки и потолок облачности, каталог
  отдаёт самое свежее, а самое свежее — это там, где спутник прошёл минуту
  назад: где именно оно нашлось, видно только очертив найденное на шаре.
  Очерчивают при этом по строке: пакетного «очертить всё» нет, а контур
  строки сетевого каталога или загрузок стои́т хода к каталогу — под рукой у
  них один ключ. У найденного геометрия приезжает вместе с выдачей и кладётся
  в кэш, поэтому его контур бесплатен и переживает следующий поиск.
- Растр без собственной привязки ложится на шар по четырёхугольнику футпринта,
  и это догадка: каталог говорит, какой кусок Земли снят, а не каким пикселем
  куда, — порядок вершин у него свой. Четырёхугольником при этом считается
  ровно одно кольцо о четырёх вершинах: снимок через антимеридиан каталог
  отдаёт двумя полигонами, по половине с каждой стороны, и растянутый по первому
  из них растр вышел бы вдвое у́же снятого. Пока в наложении есть хоть один растр с
  решёткой опорных точек (у Sentinel-1 это measurement-COG) или привязкой к
  проекции (Landsat в UTM), догадкой не пользуются вовсе — она подменяется
  ими; у продукта, где такого растра нет вовсе, снимок может лечь повёрнутым.
  В логе это видно строкой «привязка из растров не взята», а строкой выше —
  причина: система, которую нечем перевести, названа своим кодом EPSG. Форма
  при этом верна — рёбра ведутся тем же правилом, что и обводка, — а вот что
  каким углом легло, сказать нечем.
- **Камера наводится по контуру каталога, а не по привязке растра.** Правило
  «привязка из растра главнее» на наводку не распространяется: летит камера
  туда, что сказал каталог (`data-browser`, наводка по контуру либо по середине
  габарита). Там, где привязка файла расходится с контуром, — а ради этого
  случая она и читается, — снимок ляжет по файлу, а камера придёт к контуру. У
  Landsat расхождение мало и в кадр укладывается; у продукта, чей контур
  каталога заметно врёт, придётся доводить камеру рукой.
- **Система, не названная в файле, не поддержана.** Привязка берётся из того,
  что записано в самом растре: код EPSG плюс преобразование. Данные, лежащие в
  местной системе координат — а земельные участки в ЕГРН лежат именно в них
  (Ростовская область — МСК-61), — обычно не несут своей системы нигде: она
  названа словами в документе, а числа лежат голыми. Сами параметры
  `projection.rs` знает и сходится по ним со сторонними пересчётчиками до
  сантиметра, но сказать файлу, в какой он системе, сейчас негде.
- **Датум растра не пересчитывается.** Файл, объявивший чужой датум
  (`GeographicTypeGeoKey`; Пулково-42 — это EPSG:4284), ложится как WGS84 и
  уезжает на сотню метров в средней полосе. Перевод между датумами — отдельная
  геодезия со своими параметрами, и заводить её ради строки в логе нельзя;
  поэтому чужой датум **называется вслух** при чтении растра, но числа
  остаются как в файле. Молчание файла и `user-defined` чужим датумом не
  считаются: сказать о них нечего.
- Какую из частей съёмки показать, когда они — разные измеренные величины,
  сказать нечем: каталог о старшинстве газов молчит, и берётся самая дешёвая
  (`scene::rank`). Нажатие на конкретную часть при этом показывает именно её
  (`scene::about`), так что выбор есть — но только через раскрытие снимка.
- Смотреть на большом приближении есть на что только там, где лежит снимок.
  Сама поверхность остаётся бумажной — базовой подложки (мозаики, рельефа)
  нет, и вне наложенных контуров приближение по-прежнему проваливается в
  пустой фон с сеткой через 15° (это 1670 км).
- Тень под виджетом контракт принимает, а рендерер не рисует (`Shadow` в
  ui-service/types.proto): он знает прямоугольник со скруглением и рамкой, а
  тень — это геометрия за границами виджета, то есть своя ветка в шейдере и
  квад больше самого виджета. Всплывающая панель поэтому отделяется от подложки
  рамкой, а не тенью.
- Именем в сценарии прогона адресуется только то, что рисует `ui-service`, и
  только нажимаемые коробки, поля ввода и надписи: остальное себя обходу
  разметки не объявляет. У шара, канвы просмотра и границы между панелями
  (`Viewport` и `Divider`) имени нет вовсе — их сценарий по-прежнему называет
  пикселями.
- Курсор над границей панелей не меняется на «тянуть»: канала смены курсора у
  платформы нет — раннер владеет окном, а `mouse_interaction` iced считает
  ui-service, и передать её окну нечем. Что за границу можно взяться, видно
  только по подсветке под курсором.
- Вкладки не переставляются внутри своей панели: бросок в полосу кладёт
  принесённое в её конец. Порядок вкладок — свойство списка, а вставка «между
  соседями» требует зон между ними, которых в разметке нет.
- Коробочка выбора своя у каждой вкладки: один и тот же снимок, выбранный в
  поиске, в сетевом каталоге стоит с пустой коробочкой и без заливки. Хранение
  повкладочное не случайно — на нём держатся выживание выбора при новой
  выдаче, уход вместе с закрытой вкладкой и посписочный счёт в заголовке. Из
  этого же следует и предел пакетных действий: они берут выбор своего списка,
  а не всё выбранное в приложении. Контур и показ, наоборот, свойства
  приложения и одинаковы во всех списках.
- Снимок, лежащий растром, лентой не обводится, если контур с него сняли
  руками: лента живёт на контуре, и другого источника у неё нет. Полоса под
  шаром такой снимок всё равно называет, а обвести его снова можно значком
  контура в любом списке, где он есть.
- Двух глобусов сразу не бывает: модуль односоставен — одна камера, одно место
  под рендер, один набор наложений. Второй вкладки поэтому не завести: она
  одна на оба экрана.
- Размер и время у папки каталога взять неоткуда: в S3 папка — это общий
  префикс ключей, и ни того, ни другого за ней не стоит. В колонках у папок
  пусто; про содержимое сказано только то, что известно библиотеке, — сколько
  файлов из этой папки уже на диске.
- Буфера обмена в платформе нет: `ui-service` работает с заглушкой
  `clipboard::Null`, а сам он wasm-модуль — до буфера ему не дотянуться. Нужна
  сторонняя реализация на стороне раннера, поэтому скопировать путь из меню
  строки нечем; показать её в файловом менеджере можно (`app/on_reveal_path`).
- Время показывается всемирное: часового пояса у `wasm32-wasip1` нет — ни
  смещения, ни базы правил, и взять их модулю неоткуда.
- Десктопный раннер поддерживает ровно одно окно: если окно объявляют
  несколько модулей, запуск прерывается с ошибкой.
- Выбор GPU: перебор идёт по адаптерам, которые отдал инстанс, а инстанс
  десктопный раннер собирает жёстко под Vulkan (`runners/desktop/src/main.rs`);
  программные адаптеры (llvmpipe, WARP) пропускаются. Если аппаратного не
  нашлось вовсе, хост берёт программный запасным (`setup::init_wgpu`) — рисовать
  он будет, но медленно. Под Windows это значит запасной путь как единственный:
  DX12 инстанс не включает, а перебор шире собранного инстанса не бывает.
- Просмотр удалённых (нескачанных) снимков требует, чтобы сервер отвечал на
  Range-запросы. Произвольный доступ формату не обязателен: последовательный
  (PNG, полосный TIFF) читается полным проходом — первый показ по трафику
  сопоставим со скачиванием, дальше работает кэш тайлов.
- В коде wasm-модулей нельзя заводить `thread_local!` со значением, которому
  нужен `Drop`: у `wasm32-wasip1` без потоков нет механизма регистрации
  деструктора потока, и первое же обращение к такой переменной уходит в
  бесконечный цикл — без трапа и без единой строчки в логе. Модуль в этот
  момент выглядит просто зависшим на `init`. Глобальное состояние в модулях
  держится обычным `static` (`MODULE_STATE` в `veldsdk::runtime`, наружу от него
  торчат `set_state`/`with_state`): инстанс
  однопоточный и владеет своей линейной памятью, так что `static` здесь и есть
  «переменная инстанса». Для значений без `Drop` (например `Option<NonNull<_>>`
  в `ui-service/src/renderer.rs`) `thread_local!` работает.
